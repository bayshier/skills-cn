# 截图对比

对照预期结果评判图像。用户批准的设计是目标；历史基线只是较早的一次尝试，而且可能是错的。度量定位差异，绝不裁决正确性。完整的探索到实现循环使用 [design-with-images](../design-with-images/SKILL.md)。

## 工作流

1. **确立目标。** 有用户批准的参考和明确的设计要求时使用它们；不要用自己的品味替换。否则从视觉需求、事物在现实中的样子和拥有该外观的领域技能推导目标。用一两句具体的话写下它（"低角度的阳光应向东投出长影；树木填满树冠；标签在这个缩放级别下保持可读"）。
   - 当正确答案不明确——多种读法都成立、品味或产品意图的裁量、只有属主能定夺的取舍——**停下来问用户**正确答案应当是什么。把对比展示给他们。不要为了免于提问而悄悄默认基线；那会把基线错的地方固化下来。
2. **确认可比性**，让你看到的差异是真实的，而不是截图的伪影：相同的 viewport、DPR、路由/页面、冻结的时间/tick、相机意图、UI 状态、数据，以及在意的字体/资产。不可比时，修好截图设置，或只在失配无害的裁剪/特征上比较。
3. **度量已批准的设计。** 做参考匹配时，在改代码或接受候选之前，先读并完成[参考基准点](references/reference-landmarks.md)。然后按问题的规模生成产物：并排图、关键特征裁剪/放大、灰度图、绝对灰度热力图、pixelmatch diff、每图的 Sobel/边缘图、边缘差异热力图、JSON 度量。
4. **在评判整体之前先检查边界。** 对每个发生变化的视觉效果，在原生比例和匹配的细节裁剪下检查它的四边。包含效果完整的淡出和周围空间；止于组件盒子的裁剪会藏住溢出。分别比较上/右/下/左的范围，以可见文字、线条或轮廓为锚，而不是推断的 CSS 边界。检查效果穿过的每个前景特征（线、图标、文字、相邻面板）：亮度、颜色、锐度和连续性必须与目标一致。一条仍可读的线也可能被错误地压暗。把每项检查记录为 参考观察 → 候选观察 → 通过/修复/不确定，并附裁剪。用基准点表解决局部距离与对比；全图平均解决不了局部缺陷。
5. **对照目标评判每处分歧。** 对两图不同的每一处，用平实的语言说出那里实际是什么——内容缺失、相机错误、层级糟糕、对比不足、深度错误、文字重叠、布局位移、边缘被裁、意外模糊、风格不符——并判断哪一侧更接近正确。答案可以是候选、基线、都错，或真正的五五开。
6. **为有争议或高风险的判断获取中立第二意见：** 一个全新子智能体，只给两张图和中立标签，按 `references/subagent-visual-review.md`。
7. **把失配收敛到已批准的目标。** 实现某个选定设计时，记录间距、形状、柔和度、排版和层级上的实质性差异；修改、重截、重复，直到解决或用户更改目标。不要因为代码更简单就悄悄豁免一处差异。
8. **以一条结论收尾：** 候选错得少（接受；如果存在基线则重新认可基线），基线错得少（拒绝），都错（还需一轮——说明还有什么不对），或不清楚（问用户）。只有每项边界/重叠检查都通过、或有用户明确批准的偏差时才接受；不确定需要更近的证据，而不是通过。整体相似或正面的第二意见不能抵消一个局部缺陷。绝不只因更低的分数就接受，也绝不只因更高的分数就拒绝。绝不隐藏内容、模糊细节、裁掉差异，或让截图变得不真实来移动一个数字。

## 实用的度量

挑选能回答问题的度量。完整的视觉对比要报告：

- `mae`：平均绝对灰度差，0..255，越低越接近。
- `rmse`：灰度均方根误差，越低越接近。
- `diffRatio16`、`diffRatio32`、`diffRatio64`：灰度差超过各阈值的像素比例。
- `pixelmatchRatio`：pixelmatch 对灰度图给出的失配比例。
- `edgeEnergyCurrent` 与 `edgeEnergyCandidate`：平均 Sobel 边缘强度。
- `edgeEnergyRatio`：候选/当前。远低于 1 通常意味着几何、道具、标签或地形缺失；远高于 1 通常意味着噪点或错误细节。
- `edgeDiffRatio32`：Sobel 边缘发生实质差异的像素比例。
- `avgLuminanceCurrent`、`avgLuminanceCandidate`、`avgLuminanceDelta`：平均亮度及其差值。当渲染明显过暗/过亮时使用，即使更粗的距离分数在改善。
- 与场景相关的内容代理量：黑/空洞比例、类地形比例、类水体比例、队伍色比例、标签/文字掩膜比例。

对 UI/文档/布局评审，当它们胜过全局像素距离时，也使用裁剪边界、文字/前景掩膜覆盖率、对比检查、边缘裁切、元素位置和改前改后尺寸。

## 单图度量

上面的每一个度量都是拿一张图对另一张图，所以当没有任何东西可比时，它们没有一个能回答"这张截图到底有没有价值"——而且成对分数是对称的，一个巨大的距离从不说出*哪一侧*才是空帧。少数几个绝对数字可以，它们从单张 PNG 在粗网格上算出：

- `colorEntropyBits` 低于约 3.0，或 `dominantColorShare` 高于约 0.6：一种颜色占据了整个画面。稀疏的场景、未点亮的场景，或从未画出来的主体。
- `edgeDensity` 低于约 0.04：几乎到处都没有形状。空的取景、几何体主导的场景，或主体落在裁剪之外。
- `luminanceContrast` 低于约 60：雾、黑暗或霾把整幅画面压进一条带。
- 本应不透明的截图上 `transparentShare` 大于 0：截图本身就是错的。透明像素保留它残留的 RGB，所以一帧看不见的画面在被合成之前可以显得很丰富——场景度量在测量前先做合成，并直接点名不可见的占比，而不是让你自己推断。上面的成对度量仍读取存储的 RGB，因此无论哪种情况，透明度都是在这个字段里被揭开的。

这些是*起疑*的阈值，不是门禁。刻意极简的设计、夜景、空状态屏幕和白板都会诚实地触发它们。用它们决定去哪里看，然后说出画面实际在做什么——绝不为抬高一个数字而调整截图，那与裁掉差异是同一种失败。

## 距离分数

当一个针对固定配对的单个数字有用时，这个默认公式适用于结构性变化：

`distance = 0.35 * diffRatio32 + 0.25 * pixelmatchRatio + 0.25 * edgeDiffRatio32 + 0.15 * min(1, abs(log2(edgeEnergyRatio)))`

它度量的是**与另一张图的距离**，仅此而已。因为基线可能是错的，距离为 0 不是成功，距离很大也不是失败——更丰富的场景、更清晰的模型、更有力的标签、真实的深度或更好的光照都会正当地抬高它。用这个分数找到图像*在哪些地方*移动了；谁对谁错在第 5 步决定。按它度量的东西给字段命名（distance，而不是 "parity"），免得有人把它读成结论。

报告全图分数；当 UI 主导画面时，再报告一个带标签的世界区域裁剪分数。用世界裁剪分数定位渲染端的移动，同时保留全图分数，让 UI/相机的错误保持可见。

## 分数纪律

- 每次迭代都引用同一配对的前后距离，然后说明这次移动是朝向目标、背离目标，还是诊断噪声。
- 内容缺失类 bug 优先用边缘度量。一张俯视平面地图可能给出看似温和的灰度 diff，而边缘能量能证明树木、道路、城市形态或军队剪影根本不在。
- 当稳定 UI 主导画面而问题是世界渲染时，把它分割出去；同时保留一个带标签的全图分数。
- 相机不对时，像素分数只有诊断意义。先修相机意图，再评判渲染。

## 工具

把对比脚本放在技能内部或一个临时工作区，不要放进产品代码，除非产品真的需要在运行时做截图对比。

- `scripts/visual-parity-diff.mjs` 是一个可复用的本地辅助脚本。用 `REFERENCE_DIR=<png-folder>`、`CANDIDATE_DIR=<png-folder>` 和可选的 `OUT_DIR=<artifact-folder>` 运行。`REPORT_ORDER=a,b,c` 固定顺序；`CROPS_JSON=<file>` 添加带标签的裁剪（按图像 id 作为键，每个裁剪用像素坐标或 `{ "unit": "ratio" }` 归一化边界表示）。成对报告每侧带一个 `sceneMetrics` 块。
- 去掉 `REFERENCE_DIR` 即可对没有 counterpart 的文件夹运行同一辅助脚本：它写出只含上述单图数字的 `scene-metrics.json`，没有 diff 产物。用它处理孤立截图、在任何人评审之前处理整套截图，或找出一个巨大距离中哪一侧才是空的那侧。
- `scripts/visual-parity-diff.eval.mjs` 是该辅助脚本自己的 eval：它生成构造上就知道正确答案的 fixture——空的、透明的、几何体主导的、人工创作的、退化的——并断言分类、不变量和 CLI 契约。改完脚本后，用同一个 `REPO_ROOT` 运行它。在你证明错的是 fixture 而不是代码之前，绝不用放宽阈值来满足一个失败的检查。
- 其他任务沿用同一套产物，而不是往应用里加一次性脚本。缺少某个需要的配对时，就扩展这个辅助脚本。
