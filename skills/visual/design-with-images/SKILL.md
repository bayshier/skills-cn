# 用图像做设计

交付物是真正可用的设计，与已批准的参考明显匹配。图像生成负责探索目标；真实截图证明实现。仅探索的请求，交付选项然后等待选择。

## 工作流

1. **框定决策。** 阅读相关的设计技能并截取真实界面。钉死什么可以变、什么必须保持：内容、取景、配色、交互和周围的 UI。保留原始截图。
2. **生成备选。** 使用可用的图像生成技能/工具，以该截图为参考。产出一小组带标签的、彼此不同的视觉方向。以概念的形式展示，绝不能冒充已实现代码的截图。
3. **冻结选定的目标。** 使用既有批准或被授予的设计裁量权；否则获得用户的选择。把选中的图像、提示词和来源出处保存在项目的参考区。说出它的可见要求：间距与内边距、剪影、排版、不透明度、边缘柔和度、层级和位置。不要用提示词里要求的属性替代选中图像实际呈现的内容。写代码之前，先完成[参考基准点](../compare-screenshots/references/reference-landmarks.md)中的参考测量。
4. **实现设计。** 使用项目真实的组件和视觉原语。生成的 mockup 不是源代码，好写的 CSS 也不是保真度的证据。当实现约束要求不同机制时，保持预期的关系。把生成文本的错误或臆造的细节标为伪影；不要为了对齐像素而交付它们。
5. **对比并迭代。** 以可比的比例、取景和状态截取真实实现。针对**已批准的概念**运行 [compare-screenshots](../compare-screenshots/SKILL.md)，带完整上下文和变更特征的紧凑裁剪。完成它的边界/重叠检查：比较效果的每一边和它穿过的每个前景，而不只是整体柔和度和间距。把每特征的通过/修复/不确定记录保持到交接。改前改后的代码截图对比只是补充；它证明的是变化，不是对选定设计的保真。列出实质性失配，在代码里修掉，重截再比。继续，直到每个预期特征匹配或用户明确修改目标。功能测试通过、更低的距离分数，或凭记忆的"差不多了"都不是停止条件。约束一出现就披露。
6. **验证并交接。** 在相关状态和尺寸下检查真实设计，包括拥挤和低对比的情况。用 [screenshot-critique](../screenshot-critique/SKILL.md) 做一次未受暗示的评审；把已批准的参考与实际结果并排展示、清晰标注，可用时使用 [preview-shots](../preview-shots/SKILL.md)。在宣称完成或发布之前，通过同一个对比循环解决实质反馈。在运行昂贵的收尾测试套件之前，先稳住这道视觉门禁；设计仍在变化时使用聚焦检查。保留既有授权；当选定设计和发布动作都已获批时，不要再发明另一道审批门禁。

## 规则

- 保持概念、先前实现和当前实现三者分明。绝不用最新的代码截图替换已批准的参考。
- 保持真实尺寸截图作为主要证据。给派生的对齐图贴标签；绝不为了提高一致度而改变应用比例或裁掉缺陷。
- 按预期设计特征评判生成的参考，不按重渲染文字或景物的字面相等评判。明确记录这类排除项；它们不是豁免不同间距、形状或层级的许可。
- 选定的概念是要求，不是可以悄悄重新诠释的灵感。如果无法忠实实现，展示具体冲突并寻求修订后的目标，而不是把一个近似当作完成来交付。
