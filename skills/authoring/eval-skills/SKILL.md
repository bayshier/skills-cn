# 评估技能

把技能当作被测函数对待。在洁净环境里喂给它示例输入，把产物对照"好是什么样"来检查，让失败驱动修改。评估只有盲跑才算诚实：执行技能的智能体不得携带本次对话的任何上下文，也绝不能看到预期输出。泄露任何一项，你的评估就变成了应试。

## 你需要的输入——缺了就拒绝

在派生任何东西之前确认这三项。任何一项缺失或无法确定时，停下来告诉用户*具体缺哪一个*，以及一个好的版本是什么样的。不要编造案例、猜测意图，或对照一个模糊的愿望做评估。

- **目标技能** —— 必须能解析到一个真实的 `SKILL.md`。找不到时，列出你能看到的技能，询问用户指的是哪一个。
- **至少一个黄金案例** —— 技能真正会收到的具体输入：一张截图、一个提示、一个文件、一个场景。不带输入的"改进 write-spec"不是案例。
- **每个案例的标准** —— 好的产物要达到的结果，以及会使它变坏的征兆，*而不是*一份穷尽式的部件清单。受测的是技能的**判断力**，所以不要预先枚举每一条要求——那会把评估变成一致性检查，不再测试技能是否决策良好。"切片做到每片都可独立构建、可独立验证，粒度由称职的从业者来选——偷懒的巨型切片和无意义的过度切分都是失败"是评审者能够据以衡量工作的标准；"切片切得好"太薄，无法评分；一份固定的预期切片清单又太死板。写出标准和征兆；让评审者去应用它们。例外是**一致性风格**的技能——它真的要求精确命中一个精确任务——此时显式判据*就是*标准；让标准的形态匹配技能的天性，分不清是哪一种时就去问。如果用户只给出一个没有标准的模糊愿望，先把标准问出来并复述确认，然后再投入智能体。

## 工作流

1. **校验输入并引出第一性原理。** 解析技能并阅读它的**第一性原理**——它为何存在、它以什么标准要求自己；评审者正是据此评分，所以如果技能没有写清楚，就与用户澄清而不是自行发明。同时在这里确定评估模式：判断（评审者应用一个标准）还是一致性（精确命中一个精确任务）——含糊时问用户。然后打磨每个案例的标准——结果加征兆，保持在用户关心的高度上，绝不放宽成一份规定好的部件清单，除非技能是一致性风格。当你能用一句话说出技能的第一性原理、且每个案例都有具体输入和一个称职评审者能够据以衡量产物的标准时，这一步完成。

2. **盲跑，每个案例一个全新智能体。** 隔离每次运行，使行为失常的技能碰不到工作检出，且每个案例都从干净状态开始。优先从运行者的最终消息中收取产物——如果技能的输出是一份计划或文本，要求内联给出，就没有任何东西落盘泄露。当技能必须写文件时，给运行者一个一次性沙盒目录作为唯一可写根，而不是工作检出的 worktree（worktree 隔离保护的是 git 状态，不是绝对路径或越界写入）。每次运行之后，清扫工作检出（`git status`），清掉运行泄露的任何东西——隔离是尽力而为，清扫才是保证。给运行者**只有**输入和使用目标技能的指令——绝不给标准、征兆、其他案例，或你这样问的原因。当你持有每个案例一份产物、每份都来自无上下文的运行、且检出于净时，这一步完成。

3. **用一个会做判断的独立评审者评分。** 把产物、标准和技能的**第一性原理**交给一个全新的评审者——这样它对照的是技能自身的意图，而不是它的个人口味——但绝不给预期输出，绝不说"让它通过"。立足于这些原理，评审者就是一位称职的从业者：它判断工作是否以*站得住脚*的选择越过了标准，并被明确允许同时追究过粗和过细的工作。它必须为每一条结论引用具体证据——一段引文或一个指针，而不是一个数字。当标准的每一部分都有基于产物的结论时，这一步完成。

4. **把非确定性算进账。** 智能体会抖动。一次绿不是证明。对任何重要的案例或任何看起来处于边界的结论，把盲跑重跑 2–3 次并汇报通过*率*。三次过一次的技能不算修好。

5. **把每个失败诊断为技能缺陷还是坏案例。** 一次未命中，要么是技能没能驱动该行为（在这里可修），**要么**是标准错了——它要求技能不该做的事、技能无法表达的事，或惩罚了一个技能本就该做的、站得住脚的判断（告诉用户；不要为了追一个错误的标准去改技能——那只会把错误的现实固化下来）。对照 `write-skills` 的失败模式给缺陷命名：过早完成、完成判据模糊、缺少规则、没有引导词、重复、沉积、战例、无效句。

6. **通过 write-skills 修订。** 修复点名的缺陷——并且在做的过程中遵守那些编写规则：先磨利完成判据再增加篇幅，优先一个引导词而不是更多句子，不添加无效句。失败就是这次修改的规格说明；只改失败所指之处。

7. **重评所有案例，不只是失败的那个。** 一次修复可能让原本通过的案例退化。循环，直到每个案例都越过它的通过率标准，或者你能证明该技能在结构上无法表达某个案例——那就汇报这一点，而不是硬凑。

## 输出

一份简短报告：每个案例的通过率和被引用的差距；每个失败映射到的缺陷；你做的修改（或者，如果用户要求先批准，你提议的 diff）；以及重评结果。让前后的移动清晰可读——这是技能确实改进了的证据。

## 规则

- **盲跑不可妥协。** 运行者只看到输入。评审者看到产物 + 标准 + 技能的第一性原理。任何一方一旦看到预期输出，评估就作废。
- **测判断，不测一致性。** 标准是工作必须越过的门槛，绝不是答案的核对清单。如果你发现自己在列举预期的确切部件，你已经不在评估技能了。
- **隔离是尽力而为；清扫才是保证。** 无论运行如何沙盒化，运行之后都要检查工作检出并清理泄露。
- 每次运行每个案例一个全新智能体——不共享上下文，因此不会有跨案例的学习抬高后面的案例。
- 对照标准评分，不对照其他产物评分，也不用一个掩盖了标准哪部分失败的数字评分。
- 不要为了通过一个你无法为之辩护的案例而弯折技能。一个暴露了坏标准的失败案例是发现，不是 bug。
