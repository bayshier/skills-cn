# 在本仓库中工作

先读根目录 readme：产品是什么、仓库如何组织、如何构建和检查。进行中的计划与各自的规格说明放在一起，每份计划都写明下一步要做什么。如果你正在工作的文件夹里有 readme，先读它再继续。这些 readme 就是写给你的。

以上是原则。命令、标志和路径与拥有它们的代码放在一起：各个 readme、各个 manifest，以及每个工具自己的用法说明。

## 与用户交谈

用户技术功底很深，但不每天读代码。指代码没问题；第一次提到某个变量、函数或模块时，简要介绍一句。

以契约为先。当工作触及组件之间的接口（<two or three of this product's interfaces>、一个模块边界）时，先说明契约是什么样的、它如何变化，再谈其他任何事。

例行问题从证据作答。只有当答案会改变一个重要决策、且别无其他敲定办法时，才问用户。

## 证明一次变更

为迭代速度优化。度量的是到可信反馈为止的时间，不是你跑了多少流程。

运行能回答你问题的最窄检查：一个测试，然后一个文件，然后一个包。这就是日常工作的证明，包括一次提交、一次合并和一次推送。

**当一份规格说明的实现完成时，把全部检查运行一次。** 运行全部很慢，而且会占满整台机器。在此之前，一次变更由它能改变的东西来检查：它自己的测试和它触及的输出。这对一次提交、一次合并、一次推送和一个完成的功能已经足够。只有完整运行才能发现的那类失败，留到最后修；这比为每一步设门禁更便宜。

一次波及整个系统的变更，其本身并不会让完整运行提前。只要还有后续工作要做，完整运行就仍等到最后。只有当下一步工作没有它就不可信时，才提前运行。

每一次昂贵的运行都必须回答一个更便宜的运行回答不了的问题。<Name this product's expensive runs>；只做变更能够改变其结果的那些。复用仍然有效的结果，只重跑变更可能使其失效的部分。没有代码读取的文档和数据根本不需要运行。

先写测试。在改变行为或修复 bug 之前，调用 <skill: write-tests> 并遵循它的 red/green 工作流。测试产品做什么、如何失败，而不是代码长什么样。

不应改变行为的变更（重构、性能调整）必须保持输出不变，否则就必须是一次被明确点名的决策。

你看到的失败就归你修，无论它是否由你的变更造成。不要交回一个带着失败的代码库；让它比你发现时更好。

绝不为了让检查通过而放宽要求。窄的通过只证明窄的声明：说明你验证了什么、假设了什么、还有什么未完成。

不要干等一次长运行。把它放到后台，继续干活。给它一个可见的进度标识和一个停止点；绝不原样重复一次失败。

## 人们看到的东西

看真实的输出。一次通过的检查并不能证明东西在面前这个人眼里读起来好。

任何视觉变更：
- 用 <skill: screenshot-critique> 获得一次未受暗示的第二意见；
- 用 <skill: compare-screenshots> 做改前对改后、以及我们的输出对参考图的评判；
- 用 <skill: preview-shots> 展示给用户。

## 每个概念一个属主

先使用仓库已经选定的东西，再写你自己的。在创建另一个之前，先找到这个概念的现有属主。

优先一条通用规则而非特例，优先简单结构而非还没人需要的抽象。

把余量花在简单上。当某个东西相对它的预算（帧时间、启动、内存、带宽）还有富余时，用这些余量保持设计简单。不要为了让东西比需要的更快而添加机制；当余量表明机制并非必需时，把它拆掉。当某个东西取代旧机制时，删除旧机制。当一次变更暴露出重复或过时的属主时，调用 <skill: refactor-clean>。

## 并行工作保持廉价

每个并行检出都是一份完整拷贝，大文件、已安装的依赖和构建产物会随每个检出成倍增加。

- 只拉取你的任务需要的大文件。
- 在检出之间共享不会变化的东西。不要再拷贝一份。
- 源码不同的检出之间绝不共享构建产物。它们会互相覆盖对方的构建，症状是一个由别人的变更引起的错误。
- 分支合并后，删除该检出及其构建产物。
