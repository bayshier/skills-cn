# 测试审计

审计**独立证明**：如果这个测试消失，什么 bug 会溜过去？产出是一张契约到其幸存测试的映射，附有关于保留、修复、合并或删除的证据。目标不是更少的测试；而是在相同或更高置信度下更少的维护。

[write-tests](../write-tests/SKILL.md) 负责如何编写和证伪一个测试。本技能负责该测试是否增加了证明、以及该证明归属何处。[review](../review/SKILL.md) 负责收尾由此产生的变更。

## 工作流

1. **界定审计范围。** 阅读仓库和限定范围的指令，然后选定一项生产职责。找到它的测试、fixture、共享套件和 CI 选择规则。在编辑之前记录起始修订版本、本地改动和测试结果。区分既有失败与未能运行的检查。聚焦式审计选择少数有实据的候选；子系统扫荡则使用下文的完备性规则。
2. **追溯断言。** 在生产入口点和它触达的代码旁边，完整阅读每个候选（包括参数行）。检查调用方、同级的实现、重叠的覆盖，以及解释该测试为何存在的历史。当断言依赖依赖项行为时，检查依赖的代码或类型。写下断言实际检测到的东西，即使测试的名字承诺的是另一回事。
3. **在编辑之前记录处置结论。** 使用下文的证据记录。发现一旦清晰就分享；工作流不得扣留重大发现。仅审计的请求以这份证据和一个建议批次收尾，而不是以删除收尾。
4. **选定幸存的归属方。** 横向审视全部记录，寻找整层冗余，而不只是个别弱断言。指明将负责每份契约的套件，以及它必须吸收的每个独特用例。优先选择带有受控外部依赖的真实路径，而不是重放内部协作对象。另一层只有对选定归属方无法暴露的失败（例如路由或生命周期行为）才配得到覆盖。
5. **一次只改一个连贯的边界。** 当实施在范围内时，先用 [write-tests](../write-tests/SKILL.md) 把独特用例搬进幸存套件，再移除它们原来的家。扩展现有用例和 fixture，而不是克隆搭建代码。同一批次中移除新近不再需要的测试钩子和支撑代码；删除导出、包装器、重置函数、全局变量或注入参数之前，先验证生产消费者。移动套件时更新测试发现和 CI 注册。
6. **证明保全。** 把被删除断言与幸存断言对比，寻找丢失的契约和无法以预期理由失败的断言。用 [write-tests](../write-tests/SKILL.md) 证伪被修复或转移的回归覆盖。隔离临时的生产改动，在不干扰其他工作的前提下恢复原始字节，并确认针对性证明通过。基线失败单独报告；调查任何新失败。运行归属套件和同级套件，然后运行仓库要求的检查。替换静态检查时，实际演练它们所声称契约对应的那条命令或试运行。运行器读取文件期间保持文件稳定。
7. **收尾批次。** 运行 [review](../review/SKILL.md)，然后把证据记录与实际交付的内容对账。明确报告未解决的失败和未运行的检查。一个更小且干净的套件并不能证明被删覆盖是冗余的；契约映射和保全证据才能。

## 证据记录

对每个候选，记录其位置和名称、实际可检测到的失败、存在的理由、任何支撑性钩子的生产消费者，以及决定：

- **保留：** 指明被独立保护的契约。仅移动文件不改变这一决定。
- **修复：** 保留契约，但替换薄弱、误导或接错了边界的断言。
- **合并：** 指明目标套件，以及在原件消失之前它必须证明的独特用例。
- **删除：** 指明更强的幸存证明，或证明没有契约需要保护。仅凭重复的怀疑不够。

附上支撑性的源码/历史证据、由此解锁的清理、风险和验证命令。缺失证据的保留为悬而未决的问题，而不是删除。

## 虚假信心

把以下内容用作调查线索，而不是自动删除规则：

- **循环证据。** 期望输出来自被测试的同一个助手函数；fixture 从生产复制一份清单；测试把一个值与它自身比较。要找到独立于实现的期望。
- **没有主张的演练。** 执行代码行、复制标识符或罗列导出可能提高覆盖率却不检测任何可信缺陷。判断执行本身是否强制了任何有意义的东西。
- **宿主干了本该代码干的活。** mock 实现了被承诺的行为，fixture 提供了生产本应生成的确认或排序，或者持久化断言读取的是真实路径从不写入的存储。对不同依赖 API 使用同一个一模一样的假件会掩盖它们的差异。
- **变红的原因不对。** 反例命中了另一个守卫，或从未到达预期分支。要验证的是失败条件本身，而不仅仅是有东西拒绝了输入。检查每一行参数都抵达了它的主张。
- **声明冒充行为。** 源码 grep、导入列表、能力标志和内部调用形态可以在用户路径已损坏的情况下为声明背书。去追踪声明所承诺的行为。
- **同一证明的重复。** 私有助手函数测试、按提供方重放共享逻辑、以及多个层次演练同一回归，可能都在保护同一份契约。保留的是不同的传输与生命周期风险，而不是同一场景换不同文件名的副本。
- **测试在给代码续命。** 某个助手函数或生产逃生舱口存在只是因为测试在调用它。把证明移到真实入口点并移除被弃用的机制；不要用另一个仅测试可用的抽象取而代之。

## 什么配得上保留

行为包括兼容性与运维契约：API 与 SDK 形态、线上字节、提示词、默认值、配置、迁移、存储、安全、平台行为、生成的跨语言一致性、包内容、发布规则和架构边界。静态断言可以是它们最廉价的独立证明。可观测的顺序也属于此列。

问一问：该测试能否在内部重命名后存活，同时仍检测到外部承诺被破坏。精确字节对协议可能是本质性的；精确的私有标识符通常不是。慢、或与实现相似，都不足以作为删除的证据。当真实契约可以被直接演练时，不要添加对重构敏感的覆盖。

既有失败可能是产品缺陷。复现并调查它；绝不为让审计变绿而移除有效主张。范围内缺陷单独修复，在同一个宿主上让失败对照与通过的修复并存。不相关缺陷记录为后续事项并保留其覆盖。

## 整子系统扫荡

在扩大编辑规模之前先扩大清点规模：

- 清点每一个归你管的测试，包括共享套件以及集成、QA 或在线宿主中的用例。把每个测试归入一项生产职责，即使文件前缀不一致。记录基线结果和测试/支撑代码规模。
- 给每份声明一个处置结论和证据。只有当所有行都配得上同一个决定时，参数表才能共用一条记录。然后跨记录做第二轮审视，选定幸存套件和退役层次。
- 有智能体可用时，按职责委托只读发现。对共享 fixture 的编辑保持单一归属方。每个批次不得引入无法解释的失败；已跟踪的基线失败保持可见以待修复。
- 用独立评审者对比被删覆盖与其新归属方。每个上报的缺口都要用恢复的证明或否定它的源码证据来解决。证明每个被恢复的契约都能抓住一个故意植入的缺陷。
- 如果基线前进，检查任何将被删除文件中的新用例并延续其契约。遵循仓库的集成策略，然后在所得修订上重跑子系统和要求的集成检查。开始下一批次之前刷新测试发现。

## 完成标准

交接契约映射、决定与理由、生产简化、被刻意保留的有价值测试、保全缺口及其解决方式，以及实际运行过的验证。大范围扫荡还要分别给出生产、测试和支撑代码的前后规模，以及剩余批次和集成状态。规模描述的是结果；它从不设定删除目标。只有当清点中没有未经检查的条目时，才能宣称完成了一次完整的子系统审计。
