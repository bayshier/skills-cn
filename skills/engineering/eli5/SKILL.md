# ELI5

把被引用的规格说明或变更，转化为一位不生活在这份代码里的技术读者的准确心智模型。平实的语言，完整的精确度：简化讲述方式，绝不简化主张。

## 笔法

当输出必须让没有亲历这项工作的人能读懂时，其他技能指向这里。读者是技术型的——伪代码和精确的主张他们完全接得住——但他们没读过任何代码，也没读过会话里的任何消息：没有 diff、没有记录、没有这项工作沿途自造的标签。按 ELI5 写意味着：

- 把一个具体场景从头走到尾——触发事件、今天发生什么、这项变更（或未构建的替代方案）会做什么——而不是抽象地描述性质。
- 每个术语在首次使用时给出定义；绝不依赖规格说明、代码或会话自造的标签。
- 使用小的具体例子，但不用类比替换精确的主张。
- 解释控制流、顺序或时序时动用伪代码。描述"某事何时触发"的文字读起来头头是道，却把缺口藏起来；五行伪代码让门禁现形，让读者看见你漏掉的那个用例。写在决策的层面，而不是实现的层面——条件及其顺序，而不是真实的函数签名。你需要它的征兆：你的文字里出现了"只有当"、"在……之前"、"除非"或"一……就"，而读者仍然说不清第二次调用会发生什么。
- 检验标准：文字独立成立，不需要 diff、规格说明或会话记录。如果读者必须追问"解释一下这部分"，就是失败。

## 工作流

1. 通读被引用的完整产物；当规格说明本身无法确立行为时，检查当前的归属代码。未指名任何产物时，解释会话当前的变更（工作树或分支 diff）。把今天已存在的与仅是拟议的区分开。
2. 通过它对用户或运维造成的后果来解释问题，包括当前设计为何会产生它。
3. 把方案解释为一条简单的前后数据流。按职责介绍每个组件，而不是按文件名或内部符号。
4. 穷尽地清点 schema 与持久契约变更：新增、修改、删除、重置，以及刻意不动的。当游标或线上格式的切换影响存储数据或读取方时，也纳入其中。没有 schema 变更时要明确说出来。

## 输出

按顺序使用以下标题：

1. `Problem`（问题）
2. `Solution`（方案）
3. `Schema changes`（schema 变更）

结尾用一句短句说明变更之后用户应当注意到什么。

## 规则

- 以行为和边界领起；只在实现名能厘清归属或契约时才提它们。
- 区分权威记录与派生索引、缓存、汇总和呈现分组。
- 直接点明破坏性重置、迁移要求、兼容性行为、最终一致性和有意的数据丢失。
- 不要因为某处 schema 变更属于运维性质、不面向用户而略去它。
