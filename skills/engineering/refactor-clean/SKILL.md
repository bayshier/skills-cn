# 干净重构

用"假如代码库是今天设计的"它会想要的更简单形状，替换旧形状。重构不是在问题旁边再加一层兼容层；而是移动所有权，直到每个概念恰好有一个清晰的家。这是双向的：把 N 个重复属主合并为一个，也把一个过载模块拆成它一直藏着的几个属主。

## 工作流

1. 在每个被触及的路径上清扫命名，即使不需要结构性重构。追问每个名字是否描述了概念当前的范围。立即重命名有误导性的文件、符号、导入绑定和共享导出；在同一个遍次里更新每个消费者、测试、文档和智能体指令。场景名只留给场景专属代码，然后再搜一遍过时引用。
2. 给缺少单一清晰属主的概念命名——它要么在多个属主间重复，要么是几个概念熔进了一个过载模块。识别出各自应有一个属主的东西：环境、定价规则、几何来源、状态机、数据契约、渲染器阶段、API 形状、UI 状态，或测试 oracle。
3. 找出每个当前属主和消费者。把包装器、别名、遍次局部常量、复制的结构体和"临时"分支都当作沉积层，直到证明并非如此。
4. 在放宽检查或把输入变为可选之前，先做一次删除遍次。对受影响路径上的每个输入、标志、守卫、回退和适配器，追问：如果它消失，会破坏什么必需行为。追踪它的写入者、传输、读取者、校验者和消费者；把它们与权威属主对照。把冗余输入改为可选不是完成。如果移除它仍能保持必需行为，就删除该机制及其调用点、测试和文档残留。
5. 把剩余的每个概念提升到它的自然归属。挑选那个从零开始就会拥有它的模块，然后让旧调用点直接消费该属主。在同一个遍次里删除或收拢过时路径。
6. 仅为已识别的消费者、以及移除会破坏的具体行为保留兼容性。可以安全忽略的旧输入，不因它们可能仍会到来就需要解析器、校验器或适配器。如果确需一座桥，让它保持极小并给它一个移除条件；假想的调用者不算数。
7. 通过消费者验证行为，包括受影响的失败与重试路径。再到代码、测试、文档和智能体指令里搜一遍被移除的机制。只有当受影响路径上每个保留的机制都有具名消费者和它所保全的行为时才算完成；报告保留的桥及其移除条件。

## 规则

- **每一行都是债务——最好的机制是你没写的那一个。**在构建任何守卫、校验器、收敛协议或清理路径之前，有两道检查来把门：
  1. **平台已经这样做了吗？**在绕开某个组件/框架写代码之前，先读它——它的定时任务、重试、默认值和生命周期。在一个会自我吸尘的组件旁边手工造一个清洁工是纯债务，而且将来调试它的人并不知道这个组件早已让它变得多余。
  2. **它所防守的失败会改变任何真实结果吗？**把被防守的条件追踪到它的消费者。如果消费者无所谓——一个喂给不关心顺序的消费者的顺序检查、对只有我们自己代码才会产生的数据做的校验——这个守卫什么也没测，不得编写。常见形态：读时重查一条单一写入路径早已建立的不变量，于是该分支只可能在手工弄坏的行上触发。问哪个调用者可能制造坏状态；如果诚实的答案是"没有——除非有人直接改数据库"，就删掉这个分支。"它可能会不一致"不是理由；"消费者随后会做错事"才是。
  标准不是"这样写正确吗？"——防御性代码通常是正确的。标准是"如果这行不存在，什么会坏、对谁坏？"没有具体答案 → 不写这行。
- **度量变更，把糟糕的体量/行为比当作形状缺陷。**在接受一次变更之前，数清它真正付出了什么——把测试与文档之外的生产代码、把逻辑之外的注释分开算，因为被解释主导的 diff 不等于被机器主导的 diff：

  ```
  git diff --numstat <base> -- ':!specs' ':!*.test.*' ':!**/test-harness'
  ```

  然后去读新增的行，而不只是总数。**小的行为变更付出大量行数是危险信号**——它最可靠地说明这个修复是在对抗既有形状而不是贴合它：一般情形该在的地方叠了一层特例、真属主旁边引入了第二属主，或一座桥接起了本该合并的两样东西。正确做法是按代码本来想要的形状重做，而**不是**提交它并附一段"为什么不得不这么大"的解释；那段解释正是坏味道，不是缓解。

  两条诚实规则，否则数字毫无意义：本次变更本未触及文件里的格式化噪音不属于变更，必须挡在提交之外；净行数接近零仍可能藏着真实重量——一个新的 cron、表列、索引、端点、依赖或配置开关是一个从此有人拥有并维护的表面，所以要把它们从行数中单独点名。
- **不要过分看重既有架构的沉没成本。**"它已经存在且能跑"不是保留某个形状的理由——编码智能体让大规模架构切换变得廉价，所以按终态的质量来衡量重构，而不是按它替换的代码量。当行为必须延续时，用测试在消费者表面把它钉住，然后置换底下的架构——尽管多数时候连旧接缝也不该原样保留：大型重构正是把它们重画成代码库今天想要的形状的机会，而不是在新地基上忠实重建旧接口。
- 一个共享原语胜过 N 个适配器。适配器只有在外部边界上或作为短命迁移接缝时才可接受。
- **拆分拥有太多概念的模块——分解也是重构。**这是合并重复的对偶：当一个文件或函数累积了不相关的职责时，沿所有权接缝把它切开，让每一块拥有一个读者叫得出名字的内聚切片，而原文件瘦身成组合。**超过约 1000 行，文件是一个坏味道，而不是判决**——有些模块配得上它的体量（内聚的状态机、生成的表、内部紧耦合的单个算法），但一个内联注册几十条路由或处理众多领域的上帝文件是累积的职责，不是内聚。只有当每个新模块都拥有一个叫得出名字的职责、且导入压力因依赖随之迁移而下降时，拆分才是对的；若只是缓解行数、把一个概念散落到读者必须重新拼装的多个文件里，那就是错的。
- **在造新东西之前，先弄清已有什么。**写新机制之前——一个形状、计算、资产、状态机、数据契约——先在代码库里搜是否已有做这件事的、或近到可以共享的东西。只有先知道那里有什么，才能做出真正的决策：复用它、合并两个近似重复、或把共享核心抽成两者都调用的独立模块——而这个决策属于*开始之前*，不是事后补上。复用并非自动是答案；已有的东西可能是错的，或确实不同，那就有意识地新建。这条规则防止的失败是无视已有之物就动手：两个本须一致的实现随后悄悄漂移，各自重新推导对方早已定案的细节（朝向、单位、边界情况、顺序）。
- 默认不为仅开发的兼容性做保留。未交付的脚手架应立即迁移到干净契约上。
- **零血统标记：按事物是什么来命名，绝不按它从哪来。**编码历史的名字——以它拆分前的巨型文件为前缀的切片文件、`foo-v2`/`foo-new`/`foo-legacy`、以产生它的实验命名的模块、以它取代的 API 命名的包装器——对不在场的读者不携带任何信息，而当旧事物消失后还会主动误导在场的那位。检验标准：今天入职、对历史一无所知的人会选择这个名字吗？如果只有配上背景故事这名字才说得通，就重命名；历史活在 git 里，不活在标识符里。同一条规则也杀掉血统注释（"之前这是……"、"从 X 移来"）——它们描述的是 diff 而非代码，所指之物消失的那一刻就腐烂了。
  重命名是例行维护，不是独立项目，更不是要请求许可的理由。按消费者所需的规模主动去做；大而机械的 diff 不是保留误导性名字的理由。区分内部标识符与持久化键和外部契约：后者仅按上述兼容性规则、为已识别的消费者保留。不要留下维护旧词汇的内部别名。
- **宁可幂等契约，不要拒绝。**当一个操作可能被请求两次——响应丢失后的重试、用户再次点击同一个按钮、重放的 webhook——达到所请求的终态就应当成功，而不是报错。在 X 已安装在其应在之处时执行"安装 X"是成功：把那个东西返回。只有当第二次请求的含义与第一次确实不同时拒绝才正确——另一个不同的东西已占据该名字，满足请求会破坏或遮蔽它。你把事情做反了的迹象：调用者必须对你的错误码做特判才能恢复正常行为，或重试路径需要一次带竞态的"它已存在吗？"预读。适用范围超出写入：对不存在之物的删除、退订、"标记完成"开关天然都是幂等的，让它们返回 404 或 409 是把记账负担推给每个调用者。
- **把模型约束在生产实际写入的范围内。**一个允许范围超过任何写入者产出的模式——每个流程都只存一个元素的列表、没有任何东西会到达的状态——让每个消费者都为一般情形缴税。迹象：当数据只能含一个时，消费者问"但到底是哪一个？"。在写入路径上强制该约束；真实的用例到来时再放宽。
- 当分歧曾是缺陷类别时，让所有权在统计、测试或调试输出中可见。
- **重新推导代码已算出的值的检查，终将与它漂移。**独立重算几何、状态或某个派生量的测试或第二消费者，可能因一个纸面上看不见的差异——运算顺序或舍入的微妙之处——与代码不一致，并作出错误判定。导出属主算出的值，让检查消费它，这样它强制的恰是代码产出的东西：计算只有一个属主，而不是两个碰巧大体一致的属主。
- **对称或无特征的占位物，可能掩盖它所代表之物中的朝向或坐标缺陷。**无论坐标系翻转与否都渲染出同样结果的对称替身，会让缺陷一直隐身，直到真实的不对称资产揭穿它。用真实资产替换占位物时，要重新验证朝向与取景，而不只是验证它能渲染。
- 用新的不变量更新规格说明或交接内容，而不是机械的文件清单。
- 如果重构开始蔓延到无关行为，就切片：先落地共享契约，然后以可评审的遍次移植消费者。
