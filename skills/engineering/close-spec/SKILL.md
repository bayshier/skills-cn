# 收尾规格说明

规格说明在你构建时是**构建计划**，在你交付后是**理据记录**。收尾就是把前者翻转成后者。计划是切片与预测搭成的梯子；记录是代码承载不了的那层意义——它为何存在、它绝不能破坏什么、你试过什么但失败了。代码是"如何做"的唯一事实来源；收尾后的规格说明是"为什么"的事实来源，也是一张通向代码的地图。

不要总结实现。任何人都读得了代码。如果一段话只是在复述某个函数做什么，删掉它，改为一根指向那个函数的指针。

## 工作流

1. **确认已交付。** 功能已合并或在树内可运行，且其测试/截图门禁全绿。如果还有切片未经验证，就不算完成——先完成或先 [review](../review/SKILL.md)。

2. **把计划与现实做 diff。** 读规格说明的 README 和切片，然后读实际落地的东西。记录构建偏离计划的每一处：被丢弃的切片、改名的接缝、结果不同的机制、被打破的假设。偏离是最值得记录的东西——否则未来的读者恰恰要把它们重新推导一遍。

3. **移动它。** `specs/<feature>/` → `specs/done/<feature>/`（用 `git mv`）。单文件规格说明：`specs/<feature>.md` → `specs/done/<feature>.md`。

4. **把 README 改写成记录**，而不是计划。保留：
   - **概述与目的**——交付了什么、解决什么问题，用现在时（"经济按月结算"），而不是将来时（"将添加"）。
   - **理由**——为什么它以这种方式工作而不是那些显而易见的替代方案；是哪些约束和取舍逼出了这个形态。这是代码无法告诉你的部分。
   - **原则与不变量**——实现必须持续遵守的规则。什么必须保持为真；违反了什么会悄悄坏掉。
   - **指向代码的指针**——可 grep 的模块/类型/函数名、文件路径，以及钉住行为的测试。机制细节让读者去代码里看；点名入口，让他们一次 grep 就能找到。
   - **死路**——试过并被否决的方案及其原因，免得有人再走一遍。
   - **视觉来源**——曾作为待匹配基线、比较目标或外观灵感上传的任何图片。它们*就是*需求本身：它们说明了"完成"必须长成什么样，以及结果为何呈现这个形态。把它们保留在树内并从 README 引用，写明每张图来自哪里（一张真实截图、一块情绪板、一个参考游戏）以及它在驱动什么。没有它们，读者看得到结果，却看不到它被要求达到的标准。

   删去：逐切片的构建顺序、"接下来我们将……"、脚手架说明、逐切片验证清单，以及任何重新叙述代码的行文。

5. **收拢切片，保住图像。** 切片是构建时的梯子；交付之后就是沉积物。把任何耐久的东西（一处偏离、一条死路、某个切片确立的不变量）并入 README，然后删除 `slices/`。但**保留基线、比较和灵感图像**——工作曾被拿来衡量的参照物——以及仍能帮助读者判断结果的 `visualizations/` 或 `assets/`。它们是来源档案，不是脚手架：可以丢弃一条构建指令，绝不能丢弃定义了构建瞄准目标的图片。把每一张接进 README 的视觉来源脉络，让"需求从何而来"的故事在收尾后依然存活。

6. **修正引用。** 更新指向旧路径的链接。如果 `[[memory]]` 笔记或其他技能引用了该规格说明，重新指向。

7. **不带偏见地审计每一句陈述。** 生成没有写过该规格说明、也没有这段对话的子智能体，让它们逐条对照实际代码和测试检查最终文档。扇出——每节一个智能体，或把主张清单拆给多个智能体——使任何一次带偏见的通审都无法放水。每个智能体对每句陈述返回一个判定：
   - **指针**（被点名的模块/类型/函数/文件/测试）——它是否存在、含义是否与规格说明所述一致？标记过时的名字和错误的路径。
   - **不变量/原则**——它在代码中真的被执行了吗，还是只是口头断言？标记代码与之矛盾或不支持的主张。
   - **概述/理由**——与交付物是否一致、是否现在时、有没有残留的"将"/"接下来"/切片编号？
   - **视觉来源**——被引用的基线/灵感图像是否仍在树内，README 是否写明每张图来自哪里、在驱动什么？标记只展示结果却不给出所持标准的做法。

   把无支撑、被矛盾或过时的陈述当作缺陷：修好规格说明（或指针），并对改动过的主张复审。只要还有一句陈述未经核实，规格说明就没有收尾。

## 坏味道检验

- 读者能否靠读代码重建这段话？→ 删掉，留一根指针。
- 它说了"将"、"接下来"或点名了切片编号？→ 它还是计划。
- 有真实决策偏离了计划却没有被记录？→ 那正是值得保留的东西；补上它。
- 是否有你曾对照匹配的基线或灵感图像？→ 保留它并说明它在驱动什么；没有标准，结果毫无意义。

## 完成标准

规格说明位于 `specs/done/` 之下，读起来是"为什么"与"什么必须成立"而不是"怎么做"，点名了实现它的代码，保住了工作曾拿来衡量的基线与灵感图像，且每句陈述都通过了对照代码的无偏见审计。一个全新的读者不读代码就能得到意图、不变量和视觉标准——为什么做完、决策如何做出的故事——并顺着指针进入代码获得机制细节。
