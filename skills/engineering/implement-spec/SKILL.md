# 实现规格说明

将当前生效的规格说明构建至完成，每次推进一个可评审的遍次。规格说明就是实施计划；当架构变化时，用户约束与已采纳的实验证据仍然具有约束力。

一个遍次（pass，通常是一个切片）是**提交检查点，而不是停止点。**任务是整个规格说明——每个切片、每个全局 TODO——而不是第一个变绿的提交。完成一个遍次意味着开始下一个遍次，而不是交还用户。只有当规格说明完全实现（或出现真正的阻塞、需要仅用户才能做出的决策）时才停止。

**在依赖图允许之处并行工作。**当切片彼此独立时，不要一次只爬一格梯子。把规格说明的依赖图当作波前（wavefront）来读，并**把相互独立的遍次委派给并发运行的子智能体**（见"规则"）——你负责编排与整合；只把真正依赖先前工作的部分串行化。

## 工作流

1. 编辑之前，先阅读仓库 README、规格说明 README 和下一个切片。加载规格说明点名的技能。识别当前接续点、全局 TODO、必需门禁，以及必须保持绿色的内容。如果多切片规格说明缺少一份活跃的交接提示词，在第一个遍次结束前补上一份。
   对于已验证的 spike（一次性原型验证），编辑之前先应用下文的**保留胜出方案**。
2. 让计划与当前代码对齐。如果该切片会保留仅用于开发的 shim、重复的类型、脆弱的包装器或过时路径，就用更简单的架构替换它们，并更新规格说明交接内容。
3. 实现一个内聚的遍次：通常是一个切片、一个纵向检查点，或一次架构修正。保持评审面小到可审计。
4. 验证真实的契约。行为变更先运行聚焦的单元测试；浏览器可见的工作要用真实浏览器/宿主环境，并检查截图，确保主体取景完整、清晰可读，而不仅仅是非空白。在宣称一次视觉变更完成之前，需要两项额外证明：在生产路由上与变更前基线做字节/像素 diff（静态检查和重新锚定的断言在空操作上全部通过——曾有一次调色板遍次在生产帧字节完全相同的情况下交付了"已验证"），以及一次未受暗示的 [screenshot-critique](../../visual/screenshot-critique/SKILL.md)——当该遍次回应的是用户的视觉缺陷报告时，要在用户报告的取景下进行——然后才能宣布修复；实现者的眼睛已被修复本身暗示，会反复放过新鲜眼光能抓住的问题。
   绝不削弱既有的默认门禁，也绝不重新锚定失败的契约，除非先证明旧契约本身是错的。
5. **每个遍次之后、提交之前，评审变更清单并做清理。**逐行阅读 `git status`/`git diff --stat`，对每一条路径给出交代：一次性探针、截图脚本、草稿文件、`nohup.out`、临时截图目录、用后即弃的 spike/调试笔记绝不进入提交——草稿不得进入代码树。把冻结的参照物、夹具（fixture）和研究证据保存在项目的参照物或规格说明资产区。没有持久用途的文件不随产品交付。
   被委派的智能体会泄漏这类东西；负责整合的评审者要用同样的眼光重新检查合并后的代码树。

   为遍次衡量体量——度量它的成本，并在行数与其交付的行为不成比例时重做——属于第 6 步的形状遍次，按 [refactor-clean](../refactor-clean/SKILL.md) 执行。
6. 在每个遍次结束、提交之前运行 [review](../review/SKILL.md)。它把三个收尾视角排成序列——refactor-clean 管形状、code-review 管定稿的 diff、write-docs 管变更触及的文档——而你要落实这三者的全部修复。长规格说明正是沉积层层层叠加之处，所以要让形状遍次处理本遍次自身的产出：本遍次引入的仅开发用 shim、重复概念、平行抽象和兼容性包装，都应收敛为单一属主的干净契约，让代码读起来像今天设计的，而不是硬贴上去的。最后，对清理后的遍次运行 [audit-choices](../audit-choices/SKILL.md)——这是一次纯审计，把规格说明未作规定之处做出的每个决策（你自己的，以及整合时每个被委派子智能体的）连同判定追加到规格说明的决策台账（`specs/<feature>/choices.md`），其本身不改任何代码。你要根据它的发现行动：按纠正后的决策重做站不住脚的选择；对任何仅用户才能定的条目，采纳已记录的临时判断——审计永不阻塞运行。重跑受影响的检查，然后只提交本遍次的聚焦变更。
7. 更新规格说明 README 的"Next Agent Prompt"：状态、已完成的工作、下一个接续点、阻塞项、变更过的门禁，以及任何改变了计划的架构决策。
8. 把**维护检查点**作为循环的一部分来运行，而不是收官时的清理。触发时机：红色遍次之后；每两三次切片提交之后；rebase/恢复/上下文压缩之后；切换功能区域之前；证据推翻计划时；交接内容与 TODO/依赖图矛盾时；决策台账的条目聚集在同一个切片周围时；或当前活跃提示词变得难以扫读时。长规格说明会反复膨胀；清理是一次正常遍次，不是装饰性杂务。

   检查点在继续功能工作之前同时清理计划与代码：
   - 把 README 交接压缩为一份当前接续点、一份优先级排序和一份紧凑的证据台账；把过程实录移入切片文件或资产。
   - 修正已完成/已拒绝/下一步标记；删除过时的 TODO、过时的验收声明、重复的状态段落和过时的提示词。
   - 重排剩余工作的次序，让下一个红色/高风险契约显式浮现，并降级不在此路径上的分支。
   - 把任何仍然红色、过载或模糊的切片重切成更小的、可独立验证的遍次，再越过它继续实现。
   - 当早期遍次的脚手架不再拥有真实契约时，删除或收拢它。
   - 如果感觉工作偏离轨道，请一个全新的评审/子智能体审计规格说明的形状与优先级排序，然后落实修复。

   当清理对规格说明、代码形状或交接内容的改动，大到否则会让后续智能体继承过时上下文时，把该检查点作为独立的聚焦遍次提交。只有当新来的智能体无需对话历史、仅凭 README 交接、TODO 和切片图就能选出同一个下一步行动时，检查点才算完成。
9. **继续。**只要还有任何切片或全局 TODO 未关闭，就直接回到第 1 步处理下一个——同一会话内继续，不为等待确认而暂停。持续循环，直到每个 TODO 都关闭。
10. **对整个规格说明再运行一次 [review](../review/SKILL.md)。**逐遍次评审各自只是拿当时的代码评判一个切片；这一次评判的是完工的功能。把范围定为规格说明的完整 diff，而不是最后一个遍次——只有在完整 diff 的范围里，蔓延到多个切片的重复、直到每个切片都落地才显得不对的形状、以及描述增量而非功能整体的文档才可见。落实修复，重跑门禁，提交。
11. **整合决策台账，然后收尾。**当最后一个切片落地时，你逐遍次追加的 `choices.md` 是按构建顺序沉积的沉积层：早期入账的条目带着"临时——在切片 N 中再 revisit"的判定，而后续某个遍次已悄悄解决了它；被后续遍次回退的条目仍躺在那里；同一个选择可能出现两次。逐遍次规则"入账即定案，不再重列"正是让这种漂移得以累积的原因——所以最终整合是它的有意例外。归档之前，**从零重写 `choices.md`**作为最终台账：对照**最终交付的代码**（而不是它落入的那个遍次）重新审计每个入账选择，把每个临时/待后续条目收敛到其实际终态，丢弃任何被后续遍次取代或回退的内容，并合并重复项。只保留**选择本身**——不要门禁结果、e2e 证据或评审发现叙述；那些在别处报告，而且不是用户现在拥有的决策。按 [audit-choices](../audit-choices/SKILL.md) 的方式呈现：按判定分组，最没把握的排最前，每条 ELI5 且可独立读懂。*然后*用 [close-spec](../close-spec/SKILL.md) 关闭规格说明。

## 保留胜出方案

- 阅读冻结的胜出代码、配置、提示词/技能和证据。保留实际行为，包括贡献未知的怪癖。重写的规格说明或更干净的设计不能取代实测结果。
- 先移植；实验另行进行。给被委派者同样的参照物和约束。记录用户要求的差异；其他行为变更先对照胜出方案验证再采纳。
- 通过生产入口、用匹配的输入和受控的外部响应证明对等。比较计算出的请求、决策、完整输出和相关恢复路径——而不只是模板或组件测试。仅对有文档记载的有意差异做归一化。在高成本的确认之前先运行这些廉价检查，并保留原有的质量门禁。
- 缺少对等证据就意味着未完成。保留参照物并继续独立工作，而不是宣称两者等价。

## 规则

- **把独立工作委派给子智能体，让遍次并行推进。**规格说明的依赖图就是地图：只要两个或更多切片、分支（如前端 vs 后端）、子切片、复现 spike 或侦察任务彼此没有未满足的依赖，就把它们交给并发运行的子智能体（在同一条消息里生成它们），而不是自己按顺序做。当子智能体并行触碰文件时，给每个子智能体各自的 git worktree，让它们的 diff 互不冲突；共享同一批文件或同一 API 接缝的工作留在单个智能体上，避免合并混乱。每个被委派的单元仍然拥有自己的完整遍次——实现、验证、评审、聚焦提交——而你负责整合结果、解决冲突、在合并后的代码树上重跑受影响的门禁，并保持 Next Agent Prompt 的连贯。只有依赖图表明必须串行的才串行；绝不让一条车道空等另一条不相关的车道。
- 对未交付/仅开发的脚手架，向后兼容不是目标。当新架构取代它们时，删除旧路径、包装器、别名、回退模式和过时测试。
- 不许测试意外变简单。拆分宿主环境或新的测试运行器必须保留旧的默认覆盖，除非规格说明明确改变它。
- 每个干净的遍次都提交，然后立即开始下一个。绿色提交是检查点，不是停止许可。如果遍次没有变绿，不要当作已完成提交；报告失败的契约和确切证据。
- 工作未完就不停止。只要后续切片或 TODO 仍然打开，"切片 N 已完成并提交"就不算完成任务——单个切片的完成是继续的理由，绝不是交还的理由。唯一正当的提前停止是：需要仅用户才能做的决策的硬阻塞、用诚实的修复也无法变绿的门禁，或用户打断。上下文快耗尽不是停止理由——更新交接内容并继续。当你必须停止时，准确说明下一个是哪个切片以及你为何暂停。
- 保持视觉证据诚实：拼版样图（contact sheet）、GIF、截图和基线必须在预期的相机/取景下展示被评判的对象。
- 扫过该切片隐含的每一个用户可见表面。如果主视图、卡片、菜单、报告和验证夹具现在各讲各的故事，那么模型、状态或数据变更就不算完成。
- 当实现触及共享行为时，按 [write-docs](../write-docs/SKILL.md) 的原则留下文档或规格说明理由：持久的不变量和指针，而不是抄录的清单。
- 对长规格说明，保持规格说明本身可评审是一项不变量。不要让 README 变成每次尝试的实录；保持一份当前交接、一份 TODO/依赖图和一份紧凑的证据台账，细节放在切片文件或资产里。
- **人工检查点永不阻塞。**在切片的评审或签核门禁处，用 [preview-shots](../../visual/preview-shots/SKILL.md) 打开相关画面，陈述决策与选项，给用户约 5 分钟发表意见——期间继续推进其他未被阻塞的工作，绝不空转。如果用户不回应，就基于证据自行裁决，把决策及其理由记录在规格说明中（作为该检查点的解决结果），继续推进——并关闭你打开的画面（preview-shots 会清理 Preview），让长时间无人值守的运行绝不堆积窗口。goal 或实现绝不停下来等用户；它记录假设、保持可逆，让用户事后纠偏。

## 完成

当代码、规格说明交接、验证证据、评审清理和一次聚焦提交都指向同一个当前事实时，一个**遍次**就算完成——然后你开始下一个遍次。

**规格说明**完成——也只有此时本技能才算完成——的条件是：每个切片和全局 TODO 都已关闭、所有门禁变绿、整规格评审已运行且其修复已落地、交接内容显示再无可接续的工作，且规格说明已用 [close-spec](../close-spec/SKILL.md) 归档。达不到这些就是实现中途：继续。

最终交还时，按 [audit-choices](../audit-choices/SKILL.md) 呈现决策台账，而不是 diff——数天的无人监督运行靠这份台账赢得合并资格；它是用户对一切在其缺席下所做决策的评审面。交出第 11 步的**整合后**台账（终态、对照交付代码核实过、只含选择本身），绝不交出逐遍次追加的原始记录——仍带着"将在后续切片中完成"判定的台账等于告诉用户：你从未回去确认它是否真的完成了。

**交还的收尾要说清你新增的体量——永远放在最后，台账之后。**台账说明决定了什么；这部分说明付出了什么代价。对整个运行给出一张简短表格：

| | 新增 | 删除 | 净变化 |
| --- | --- | --- | --- |
| 生产代码（不含注释） | | | |
| 注释 | | | |
| 测试 / 宿主环境 | | | |
| 规格说明与文档 | | | |

然后用一段话点名本次运行新增的**结构性**表面——新的 cron、表列、索引、端点、配置开关、依赖——因为用户从此要拥有并维护它们，而单纯的行数会掩盖这些。排除本次运行本未触及文件中的格式化噪音；如有排除，要明确说明。

无论数字如何，直白报出。小的行为变更换来大的净增行数，这是要报告的发现，不是要掩埋的数字——如果你是在这里才注意到，而不是在造成它的那个遍次，要说明是哪个遍次。


**切片不是唯一的范围单位。**规格说明还记录*决策*——台账行、决策表条目、不变量——而一项决策可能在规划时达成一致，却从未变成切片，尤其当它与切片的主题正交时。此时"所有切片已关闭"看起来像完成了，而那项决策却被悄悄搁置。在宣布规格说明完成之前，把每一条已记录的决策对照交付代码核实，而不只是对照切片清单：每条决策要么已实现，要么被显式标记"无需代码"。没有属主切片的决策是典型的无声遗漏——close-spec 审计是它的最后防线，而不是第一道防线。
