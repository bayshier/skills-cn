# 代码评审

依照以下原则评审 diff 或指定文件。

## 1. 命名必须反映当前现实

- 变量和函数名应描述它们现在是什么，而不是它们过去是什么。
- 如果底层机制变了（例如 FUSE → NFS），所有相关名字都必须更新。
- 自问：新读者会被这个名字迷惑吗？

## 2. 不留过时引用

- 重构之后，grep 旧方案的残留引用——死掉的检测逻辑、被放弃的特性开关、提及已删代码的注释。
- 如果某样东西试过又回退了，抹掉所有痕迹。代码库应当看起来像当前方案从来就是计划本身。

## 3. 简化检测与守卫逻辑

- "这个功能能不能跑"这类门禁应该只检查真正要紧的那一件事。
- 当一个检查就能覆盖时，不要串联多重后备检测（二进制存在 OR 源码存在 OR 工具链存在）。

## 4. 注释记录"为什么"，而不是"发生了什么"

- **保留：** 非显而易见的技术发现、平台怪癖、"如果你删掉这里，X 会因为 Y 而坏掉"。
  - 好：`// com.apple.provenance causes SIGKILL when spawned as child process`
  - 好：`// umount while server is alive panics the macOS NFS client`
  - 好：`// NFS client uses cookie verifier to decide if cached readdir is valid`
- **删除：** 讲述试过什么、放弃了什么、改名了什么的故事性内容。
  - 坏：`// We changed this from cp to cat to work around the provenance issue`
  - 坏：`// Wrapper added because FUSE-T was zero-padding (see commit abc123)`
  - 坏：`// Previously this was called fuseAvailable but we renamed it`
- **删除：** 只复述代码做什么、不增添推理的注释。
- 很多时候根本不需要注释。

## 5. 把安装期与运行期分开

- 安装脚本负责准备前置条件（工具链、系统依赖）。
- 运行期命令负责编译、缓存、二进制管理。
- 不要混在一起。如果安装脚本在编译运行期也要编译的二进制，那其中之一就错了。

## 6. 不留中间产物

- 在迭代过多个方案之后，审计那些只作为垫脚石存在的逻辑。
- 如果为方案 A 加过变通处理，而你已切换到方案 B，就删掉那个变通，即使它无害。
- 代码读起来应当像是一个早已知道正确答案的人从零写出的。

## 7. 改动之后收紧保证

- 当一次改动让某事成为保证（例如变量现在总会被赋值、文件总会被创建、函数总会返回），审计仍在防御旧"可能"状态的下游代码。
- 对不再可能为空的值做的冗余判空、兜底默认值和 `if (x)` 守卫都具有误导性——它们暗示一种并不存在的可能性。
- 当重新赋值不再需要时，优先 `const` 而非 `let`。
- **绝不压制信号——修复根本原因。** 未用参数加 `_` 前缀、`// @ts-ignore`、`eslint-disable`、`as any`——这些都在掩盖真实问题。如果参数未被使用，删掉它并把删除级联到每个调用方。如果类型不匹配，修类型。运行检查器，修掉每一个错误，再重复。跨大量文件的机械性修改正是智能体擅长的事——不存在"调用方太多"。

## 8. 改动缠成一团时，干净重来

- 如果一个文件经历了三轮以上相互冲突的编辑，`git restore` 它，只重新应用需要的部分。
- 不要试图对一团糟做外科手术式的修复——干净重来更快、更不易出错。

## 9. 测试必须验证真实值，而不只是集合大小

- 测试去重、归一化或幂等操作时，对**存储的值**做断言，而不只是 `toHaveLength(1)`。
- 光凭长度证明不了逻辑有效——坏掉的归一化器可能悄悄丢掉一个输入，或存下两个碰巧匹配的不同归一化形态。
- 模式：以格式 A 添加值，再以格式 B 重新添加，然后同时断言数量为 1 **且**存储值等于预期的归一化形态。
- 坏：`expect(data.phones).toHaveLength(1)`——归一化坏掉了也能通过
- 好：`expect(data.phones).toHaveLength(1); expect(data.phones[0]).toBe('+12125551234')`——证明归一化识别了两种格式

## 10. 不要薄包装或纯再导出模块

- 如果一个模块只是转发另一个包的函数或类型，删掉它，直接导入原始包。
- 不要为脚手架代码或未发布分支的工作保留本地兼容垫片。直接替换脚手架。
- 再导出桶文件没有用处，除非它们定义了具有项目特有语义的真实公共边界。避免创建唯一职责是 `export * from ...` 的文件。
- 优先直接使用上游 API 名，而不是发明本地别名，例如为 `loadSkills()` 起名 `discoverAll()`。

## 11. 只围绕真实的职责边界做抽取

- 不要只为减少行数而拆文件。新文件应当拥有一项读者说得清的连贯职责。
- 当相关策略、状态转换、资源处理或领域特定行为集中在一起时，才抽取模块。
- 如果调用方仍需理解全部细节才能使用，就不要把一次性助手函数挪进新文件。
- 好的拆分通常会降低原文件的导入压力，因为依赖随它们服务的职责一起迁移。
- 如果抽取增加了总体间接层次却没有厘清职责归属，就让代码留在原地。

## 12. 让测试与实现解耦——端到端驱动系统

最有价值的测试套件是与它所覆盖的实现解耦最深的那一个。解耦到这种程度：通过驱动前端来演练后端，通过走用户所走的同一个入口来演练模块。戳内部细节的测试会冻结内部；驱动公共表面的测试让你可以自由重构下面的一切。

- **优先选择仍能给出快速、确定性信号的最外层入口。** CLI 二进制 > 顶层导出函数 > 内部助手 > 私有方法。如果用户调用的是 CLI，就针对 CLI 写测试。如果用户看到的是 TUI，就沿真实按键命中的同一条输入管线驱动它，并对渲染出的帧做断言，而不是对中间状态。
- **测行为，不测结构。** 对可观测结果做断言——退出码、stdout、渲染输出、磁盘文件、HTTP 响应、持久化的行。不要断言哪些函数被调用、以什么顺序、带着哪些中间形态。那些是应当可以自由变更的实现细节。
- **测试通过应当意味着真实用户得到正确结果。** 如果生产路径已坏而测试仍能通过，那测试接线就错了。常见坏味道：对被测对象打桩、绕过路由器/分发器/解析器、手工构造本应由生产代码从输入构建的内部事件。
- **宿主的接线方式必须与生产一致。** 实践中总会被设置的可选输入也是契约的一部分——在宿主里传入等价物（例如一条已稳定的状态流、模态配置、相同的环境变量）。如果你只有对着真实环境跑才发现了某个 bug，说明宿主漏掉了生产会设置的某个东西；修好宿主，让下一个同形回归被测试套件抓住，而不是被用户抓住。
- **耦合的测试是重构税。** 当重命名一个内部函数或移动一个模块会打破几十个测试、而用户可见行为毫无变化时，套件就是在测错误的层。针对外层表面重写这些测试，并删掉脆弱的那些。
- **单元测试留给真正精巧的纯逻辑**——解析器、归一化器、调度器、带有微妙不变量的状态机。其余一切作为集成或端到端测试更有价值。

## 13. 失败的检查可能是工具链缺陷，而不是代码缺陷

在手写一个类型、加一个类型转换、固定一个值或重构代码以让某个检查器（类型检查器、编译器、linter、测试运行器、构建）通过之前，先确认失败是代码缺陷，而不是工具链/环境的产物。为迁就一个坏掉或不匹配的工具而给代码打补丁，是掩盖真问题的变通——即"绝不压制信号"规则的上一层版本。

- **在报告失败的那套确切工具链下复现**——用 CI/部署的版本和配置，而不只是你本地的。如果本地检查跑的是不同版本，绿色证明不了任何事：一个被固定的预发布版、一个预览构建、或你的机器与 CI 之间的版本漂移，都可能让完全相同的源码在本地通过而在 CI 失败（或反过来）。
- **如果同一源码在真实/固定的工具下通过，代码就是对的**——修复属于工具链（固定版本、修配置），不属于代码。当输出含糊时，直接探查工具本身——强制它打印它实际算出的值、类型或错误——而不是猜测原因。
- **保持本地 == CI。** 确认为合并/部署把关的检查运行的是与部署相同的工具链；版本漂移会让每一个绿色检查都可疑，"本地通过了"也不再是部署会通过的证据。

## 14. 身份来自认证，绝不来自调用方

- 从经过认证的请求（API 密钥、会话或经验证的内部密钥）解析操作者身份——org/tenant/workspace id、用户 id、actor——绝不从调用方提供的参数解析。从参数读取 `actorId`/`orgId` 的公开变更操作是伪造入口，不是功能。
- 唯一例外是受信任的内部调用：只有当有效的内部密钥在场时才接受调用方提供的 actor；否则从认证派生身份并拒绝所提供的 id。
- 要把范围限定到认证范围内的某个子对象（特定频道、分享、应用），取_子_ id 并验证它属于由认证派生的父对象——不要信任请求体里并行的父 id。

## 15. 公开 API 动作是薄认证 + 分发，不是内联业务逻辑

- 公开路由做认证、校验、派生身份，然后分发给拥有该工作的模型函数或内部动作。保持这层包装很薄——它是认证/运行时边界。
- 不要因为"只有 3 行"就把第三方 SDK/分析/邮件逻辑内联进公共边界。把它推到分发之后。
- 在 Convex 中尤其如此：不要只为满足一个动作就给容纳多个动作的文件加 `'use node'`——它会强迫文件里的每个动作都进入 Node 运行时。拆分：认证+分发（默认运行时）→ `services/<thing>.ts`（`'use node'`，持有 SDK 调用）。

## 16. 公开端点以最小范围交付

- 一条路由，每次请求一项。在具体的第二个调用方出现之前，不要预先添加 `/batch` 变体、分页列表或过滤参数。
- 把 schema 内联在路由里；当没有任何东西复用它时，不要把 4 行的 schema 提升到共享的 `schemas.ts` 里"以备复用"。除非请求体真的无界，否则跳过请求体大小上限。

## 17. 复用既有类型——派生，不要重复声明

- 如果一个类型在上游已存在（schema 校验器、协议包、生成的客户端、SDK），直接使用它——不要内联重复声明它的形态，哪怕部分也不行。重复声明的形态会漂移。
- 对于变体，派生它：`Pick`/`Omit`/`Partial`/`Parameters`/`ReturnType`/索引访问/`Extract`/`Exclude`；Convex/Zod 等价物 `Infer<typeof V>`、`FunctionArgs<typeof api.x.y>`、`z.input/z.output`。
- 坏：在既有 `User` 旁边写 `type UserSummary = { id: string; name: string; email: string }`。好：`Pick<User, 'id' | 'name' | 'email'>`。

## 18. 在索引处过滤，绝不用 `take()` + 后过滤

- 当列表查询要返回某个表的子桶中的行（活跃 vs. 归档、`status === X`）时，过滤必须由**索引**完成。不要对未过滤的查询 `.take(N)`，再在 JS 里 `.filter()` 出你要的桶。
- 为什么会坏：`.take(N)` 返回索引顺序开头的 N 行。如果开头全塞满_另一个_桶，后过滤即使桶里有几百行更早的行也返回零。`take(N*2)` 只是推迟失败。
- 模式：把判别字段放进索引并使用 `.withIndex(..., q => q.eq(...))`，对"存在"桶使用 `q.gt(field, 0)`（Convex 把 `undefined` 排在有值之前）。`.first()`/`.unique()` 和"是否存在某个 X"的探测同理。

## 19. 绝不 `.collect()`——用 `.take(N)` 为读取设界

- Convex 的 `.collect()` 无上限地读取每一个匹配行。对任何随时间按租户累积的东西（会话、事件、台账行、审计行），第一天没问题的查询最终会在一次响应式 tick 中拉取数千行，悄悄拖垮整个客户端的响应性。
- 用 `.take(N)` 替换 `.collect()`，N 是明显高于当前工作集的安全上限（100、1000）——这是针对病态数据的封顶，不是 UX 分页器。`.withIndex(...).filter(...).collect()` 同理。
- 如果你确实需要每一行（迁移、管理员导出、一次性维护），用注释说明，并从可取消的 mutation/action 运行，绝不用响应式 `query`。

## 20. 不要只为改名或补默认值而重映射行

- 逐字段复制只为改名两个字段或把 `undefined → false` 归并的对象字面量 `.map()` 是噪音，而且它们会在有人更新映射之前悄悄丢掉新列。如果消费者需要每个字段，就返回整行；如果只需要子集，用 `Pick`/`Omit` 或解构加重 rest。只有当新名字实质上更清晰时才改名；只有当下游真的无法处理缺省时才补默认。
- 用解构 rest 一次性剥离仅存储用的字段（`_id`、`_creationTime`、内部 id）。好：`return rows.map(({ _id, _creationTime, ...row }) => row)`。

## 21. 内部 API 不带版本或兼容机制

- 当生产者和消费者都归我们所有（我们自己的应用、服务和函数）时，不要加 `protocolVersion` 字段、版本协商、能力标志或"万一对方更旧"的分支。部署本身就是版本。
- 唯一真实的兼容轴是字段，不是版本——而且它是不对称性，不是旋钮：**严格解析请求**（拒绝未知字段），**宽容解析响应/事件**（忽略未知字段）。这让生产者可以在消费者不同步发版的情况下添加字段，这恰好覆盖我们实际拥有的唯一偏斜（按自己节奏更新的组件）。
- 坏味道：线上 schema 中一个没有任何东西读取的版本字面量；唯一调用方是我们自己部署代码的 `if (payload.v >= 2)` 分支；对响应使用的严格解析器，它把服务端每一次增量变更都变成破坏性变更。
- 例外：真正的外部 API（我们无法替消费者重新部署）在路由层做版本（`/v1/`），绝不在字段级。

## 22. 必须保持一致的东西要有唯一归属方

- 当两个声明必须保持一致、却各自可以单独变更时，它们就会漂移。给共享决策安一个家，让每处使用都从它组合而来——与别处已有一组相重复的平行枚举、选择器列表或 switch 是常见情形（派生形态见规则 17；本条是适用于一切必须一致的值的更一般规则）。
- 更难的一半：当近亲物合法地不同时，在代码里说明差别的理由。两个本可相同的东西之间无文档的差异，与漂移 bug 无法区分——读者分不清那是意图还是疏忽。

## 23. 不要把一次性使用的值提升为具名 const，除非这名字配得上

- 提升到模块作用域却只被引用一次的 `const` 只增加间接而不产生回报：读者必须跳到声明处才能知道值，而这个名字复述的不过是内联值加一句短注释就能说清的事。把它内联在唯一调用点，让注释承载"为什么"。
- 当至少满足下列一条时，单次使用的具名 const 是合理的：
  - 它是**经常变化的配置**，或是运维/读者被期望去调的配置（作为旋钮分组在一起的超时/限额、特性阈值、会被调整的重试预算）。
  - 它**紧挨着相关的 const**，并从这一簇中获得意义（一组 `*_TIMEOUT_MS`、一张限额表、同级的枚举成员）——分组本身就是文档。
  - 独立声明它**在结构上有意义**：它作为模块公共表面的一部分被导出、被某个类型引用，或与它所参数化的数据/文件同处一地，好让未来的第二个调用方找到它。
- 否则内联。评审者检验：如果这个名字的存在只是为了给一个只用一次的字面量贴标签，而它既不常变、也不住在亲戚旁边，那它就是噪音——把它折进调用点，用一句注释解释这个值。
- 坏：`const STOP_SESSION_CONNECT_TIMEOUT_MS = 5_000` 孤零零地声明，只在唯一一处 `runAction({ connectTimeoutMs: STOP_SESSION_CONNECT_TIMEOUT_MS })` 中使用。
- 好：在调用点写 `connectTimeoutMs: 5_000, // 5s: a cold sandbox must not hang on the 60s default connect`。

## 24. 批处理循环隔离逐项失败——一个坏项绝不让其余项饿死

- 任何对独立工作项的循环（扫荡、cron 批处理、队列清空、机群轮巡、扇出）都必须逐项捕获异常并继续——把失败收集进结果（一个 `failed` 列表）或记日志。未捕获的逐项抛出会中断整轮，而且因为运行器（cron、调度器、同步轨道）下一 tick 会重新选出同一个有序集合，一个必然失败的项就成了永久的队首阻塞：它后面的一切永远重新排队，而指标却显示任务在"重试中"。
- 在事务性上下文中（例如处理一页并推进游标的数据库 mutation），失败更糟：未捕获的抛出还会回滚游标/进度写入，同一页将永远重跑。被捕获的错误能让事务存活——但失败项自身在抛出前的写入会保留，因此要在写入幂等或可安全重跑的项边界处捕获。
- 失败即提前退出只有在失败可证明是批次级时（共享下游不可达）才正确，绝不能用于单项错误。如果整轮的调用方需要失败可见性，就捕获-记录-继续，并在整轮完成后重抛第一个错误。
- 即使有隔离也要提防顺序陷阱：如果成功项留在候选集里（例如每次重试都对阻塞项之前的所有东西重新做快照），扫荡还需要让它的选择排除已完成的工作。
- 可接受的形态：逐项 try/catch 并在结果中放 `failed`；按项为键的 `Promise.allSettled`；捕获-记录-继续后整轮结束再重抛。
- 坏：把 `for (const ws of candidates) { await archive(ws); await mark(ws) }` 放进每小时一次的 cron——一台不可达的 VM 会永远冻结它后面的每个候选。
- 好：同一个循环，把逐项整体包进 try/catch，将 `{ workspaceId, error }` 推入返回给调用方的 `failed` 数组。

## 25. 改用户看见的名字，就要扫测试看见的名字

- 面向用户的文案、可访问名称、路由和 `data-*` 属性，对不在你门禁内运行的测试层是承重的——真实预发环境的宿主、旅程套件、外部监控。一次让所有本地门禁保持绿色的改名，可能在几小时后于别人的会话里悄悄弄坏它们。
- 当一次改动重命名可见文案或重构某个表面时，全仓库 grep 旧字符串/选择器——明确包括测试宿主和 e2e 包——并在同一批次更新每一个锚点。改名的 diff 就该是扫荡的 diff。
- 评审者检验：从 diff 中挑一个改过名的字符串，全仓库 grep 它。diff 之外任何幸存的命中都是等着下一次线上运行爆发的破坏。
- 结构胜过文案：旅程需要锚点时，优先用表面自有的 `data-*` 属性而不是它的显示文本——这样产品文案可以随意变化而不碰测试。当结构属性已经存在时，标记那些锚定在文案上的旅程。

## 26. 让代码比你发现时更好——整齐的 diff 不值得拿凌乱的仓库去换

- **绝不为了保持 diff 聚焦而回退顺手之喜的改进。** 如果格式化器、linter 或 codemod 顺带清理了你的改动没碰的文件，**把这些也提交**（如果动静大就单独成一个提交）。回退它们优化的是评审时 diff 的观感，却向此后每一轮工作收税——同样的成本再付一次，然后再回退一次。仓库的健康高于 diff 的整洁。
- **死物由发现它的那一轮处理。** 死列、死参数、死函数、死导出，或唯一调用方是测试的测试——当场删除，连同为它辩护的注释。不要记录成待办；一张纸条就是一次延期，下一个读者还得重新推导它已死。
- **你发现某条注释是假的，它就是缺陷。** 就地修好。错误注释比本可纠正它的 diff 活得更久，并且主动误导——比没有注释更糟。
- **修复你的改动暴露出来的潜伏 bug。** 让一条很少运行的路径每次都运行的工作，会暴露顺序 bug、不可达的清理逻辑和从未触发过的断言。这现在是你的 bug：因为是你让它变得可达。
- **在"改进"之前先验证。** 删除或重写之前，确认那东西真的死了、错了、坏了——grep 消费者，跑测试。自信满满地删掉某个承重物，远比你正在修的凌乱更糟。
- 边界：不要把不相关的*行为*变更夹带进特性提交，也不要因为不喜欢某个相邻模块的形状就重写它。本条规则涵盖机械性整洁、死代码、错误注释和你使之可达的 bug——不包括顺手的重新设计。
- 评审者检验：这次改动落地之后，仓库里是否有任何文件比改动开始前**更糟**，或带着一条明知错误的陈述？如果有，这一轮就还没完。
