# 审计决策

给定一个好的决策，智能体会忠实地实现它；而任务中任何未明确说明之处，它都会自行做出决策——悄无声息，diff 也不会标记出来。逐行评审成千上万行改动无法扩展，而且它检查的是执行过程，而执行大概率没问题。能扩展的审计对象是**决策**：找出实现者自行做出的每一个决策，对这份清单逐一评判，并记录判定结果。

这关乎架构，甚于关乎 bug。一个实现可以运行得完美无缺，却仍然建立在用户从未做过的决策之上——一种数据形态、一个存储位置、一个依赖、一份 API 契约、一次以内存换速度的取舍——而其中每一项都是未来工作的承重结构。用户需要知道它们，不是因为它们错了，而是因为它们如今已归用户所有。

这是一次纯粹的决策审计——不涉及修改代码，且可以在任意时刻调用。其任务是**向前追溯**：走查本次会话走过的每一步，以及每个子智能体走过的每一步（存活中的实现者自行追溯；否则从其报告、会话记录和 diff 中重建），并揭示每一个代用户做出、却不在原始规格说明或提示之内的决策。这份决策台账取代阅读代码，成为用户的评审界面——这正是全部要点。对判定结果的处置（重做某个不合理的决策、落实某个临时决定）属于调用方：运行中的实现工作流，或读完报告后的用户。

两种进入方式，同一次审计：

- **由工作流调用**（每轮或每个切片一次）：审计该轮，把条目追加进台账，然后返回；工作流在交回结果时呈现累积的台账。
- **由用户直接调用**：审计眼前的全部工作成果（某个会话、分支或具名变更），并立即呈现报告。只给建议；不做任何改动。

## 工作流

1. **引导并追溯。** 当实现者报告完成时，问它：*"在做这件事的过程中，你做了哪些自己没有把握的决策？全部列出来。*"——但要把这份自报当作起点而非边界：智能体会漏报。亲自追溯历史——会话的步骤、子智能体报告、diff、提交——收集每一项存在于工作成果中、却不在原始规格说明或提示里的决策。扫遍架构类目，而不只是可疑的修复：数据形态与格式、存储与命名方案、API 契约及其错误行为、新增的依赖、并发/性能取舍、对范围的解读、未来代码会模仿的模式。审计你自己的会话时，以同样的方式追溯你自己的步骤。计划中明确委托给实现者自行处置的决策属于裁量，不是审计项。
2. **依据证据对每项决策分级定性。** 是计划所迫，还是自行发明？自行发明的那些要重点审视：这是通用解法，还是只为那一个失败案例量身定制的修复？对每项决策给出判定：**合理（sound）**、**不合理（unsound）** 或 **需用户定夺（needs-user）**——判定之外还要给出**置信度**：该审计有多大把握认为用户当初也会做出同样的选择。置信度决定报告的排序。needs-user 只保留给真正只有用户才能做的决定（品味、产品方向、外部成本）；每条 needs-user 条目都要记录一个可逆的推荐临时决定，使无人监督的调用方无需等待即可继续。审计绝不使运行停摆：每条条目都是交付出去供执行或评审的判断，不是一个会让流程中断的提问。
3. **陈述修正后的决策，而不是勾画一个补丁。** 对每项不合理的决策，条目要指明工作应当基于哪个决策重做——那条在一般情况下必须成立的性质——而不是在其上再叠一层修改。在坏决策之上打补丁，保住的还是那个坏决策；重做本身是调用方的事，在台账被评审之后进行。
4. **把每项决策存入台账**（见下文），并把承重的合理决策提升进计划的交接内容，让后续轮次把它们当作既定前提继承，而不是重新决策。
5. **呈现台账：按判定分组，按置信度排序。** 审计的交付物就是台账，交给接下来行动的人——运行中的调用工作流，或运行结束时的用户。每个判定组对应一种行动——needs-user（做出决定，参考其中的临时决定）、unsound（重做，参考其中的修正决策）、sound（知悉：这就是用户如今拥有的架构）——组内按置信度排序，置信度最低的在前。当台账很长时，用全局置信度最低的两三条决策开篇，不论它们属于哪组：即"先评审这几条"那一行。sound 组不可跳过。只有无关紧要的裁量（内部命名、外观性的选择）才压缩成一行计数。

   **每条条目都按 ELI5 写——默认如此，而非应请求才写。** 读者没有亲历这场会话：每条条目都要用 [eli5](../eli5/SKILL.md) 的笔法来写——一个从头走到尾的具体场景（触发事件、这项工作今天的行为、未构建的替代方案会做什么），每个术语在首次出现时给出定义，当决策涉及控制流、顺序或时序时，给出决策层面的伪代码。"被门禁拦下的请求会被丢弃，而不是延后"是一个标题，不是一条条目。压缩后会让用户追问"这条解释一下"的条目就是失败的；台账必须脱离 diff、规格说明和会话记录独立成立。

## 决策台账

一份比每一轮都活得更久的专属文件：`choices.md`，放在计划旁边（当工作由规格说明主导时为 `specs/<feature>/choices.md`）。每项被审计的决策一条条目：

- **时间（When）**——它落在了哪一轮或哪次提交。
- **决策内容（The choice）**——一行标题，然后是 ELI5 场景：触发事件、这项工作今天的行为、未构建的替代方案会做什么，术语就地给出定义。
- **缺口（The gap）**——计划中未明确说明、从而迫使其自行决定的之处。
- **影响范围（The reach）**——这个决策约束或解锁了哪些未来工作；用户为何需要知道它的存在。
- **判定（Verdict）**——合理（sound）/ 不合理（unsound）/ 需用户定夺（needs-user），附一行理由。不合理：给出重做所依据的修正决策。需用户定夺：给出推荐的临时决定及其撤销方式。
- **置信度（Confidence）**——审计有多大把握认为用户会做出同样的选择（低 / 中 / 高）。决定报告排序，升序。

台账规则：

- 已入账即为定论：已在台账中（或已提升进计划）的决策是后续轮次的既定前提——不再重列，不再重议。
- 台账是计划质量的信号。条目聚集在同一个切片或领域，说明计划在那里雾气弥漫——重新切片，或把那部分送回规格说明流程，而不是永远对同一类决策反复定性。
- **ELI5 在每一次改写中都要存活。** 上述条目格式——标题加上走查过的场景、术语就地定义——是*存储*格式，不是呈现上的修饰。当条目被汇总、合并、收尾时复审，或复制进最终台账时，每条幸存的条目都要保留（或找回）其完整场景。已知的失败模式恰恰是这种压缩：一次收尾改写把已入账的条目缩成标题，产出的台账读者只能去拷问——"检查点按邮箱顺序加载行，并在较靠后的引用拥有更早的 createdAt 时拒绝该列表"读起来像已有定论，但只有走查过的版本（两个会话、各会话内部无法相互比较的序号、共享的插入时间戳时钟）才能让读者真正评判这个决策。丢弃场景的汇总即使每一条事实都还在，也是失败的——保留了场景、却依赖构建过程自造且未在使用处定义的标签（"重试信封"、"证据接缝"）的汇总同样失败。

## 规则

- **"它能跑"不是对该决策的判定。** 反复出现的坏味道是巧合式修复：调整过大小的缓冲区、加大的超时、或某个特例分支，其量级恰好盖住了失败的输入，而根本原因仍在潜伏。要问是什么性质*在一般情况下保证*修复有效；如果答案是"这个用例能通过"，那么即使代码是绿的，该决策也不合理。
- 宣告成功之时是风险最大之时——实现者的自信恰在其未经审视的决策即将被合并时达到顶点。绝不因结果看起来干净而跳过审计。
- 非平凡的工作得到一张空清单是危险信号，不是通过。追问：任务留下了哪些未明确之处？总有什么东西填了这些空白。
- 审计不改动任何代码、测试或构建状态。发现一个不合理的决策就是交付物，而不是修复它的许可——记录修正后的决策，让代码树保持审计时的原样，使台账与代码树对调用方正在决策的对象达成一致。收集证据不受限制：可以读任何东西、运行现有测试、写临时探针——但在交回之前移除每一个探针。

## 完成标准

当本轮中每一项自行发明的决策都有带判定的台账条目、每条不合理的条目都指明重做所依据的修正决策、每条需用户定夺的条目都附带可逆的临时决定，且台账已呈现给接下来行动的人——按判定分组、组内置信度最低者在前、每条条目无需追问即可按 ELI5 读通——而代码树分毫未动时，审计即告完成。交回时展示的是 diff 而非决策，或审计期间动了"修复"，都不算完成。
