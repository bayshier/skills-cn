# 性能审计

找出那些没有有效上界地增长、或不断重复却毫无进展的工作。产出一份有证据支撑的台账或报告，然后优先选择能保全恢复能力的最小修复。

## 工作流

1. **追踪热点路径。** 找出反复出现的同步、轮询、流、重试、队列、定时任务、文件系统遍历和请求期读取。沿每一条的生产调用方一路跟进；忽略仅测试使用的路径。
2. **计算放大倍数。** 用具体单位陈述触发条件与最坏情况下的工作量：行数、查询数、页数、条目数、字节数、任务数、重试次数或整文件重写。区分"有界的大常数"与"随历史、租户、路径或故障时长增长的工作量"。
3. **检查前进性。** 对每一次重试、固定前缀批处理、截止点或过渡期轮询，确认下一次尝试之前有什么会改变。如果没有任何东西必须改变，它就可能永远循环或永远饥饿。检查局部修复是否只是把同样的工作推迟。
4. **证伪严重性。** 检查现有的上限、索引、退避、截止时间、负责恢复的组件以及调用频率。排除那些已被足够廉价地限制住、或能持续自愈的发现。
5. **先记录后修复。** 如果项目维护着性能台账，按其既有惯例追加每一条有依据的发现和重要的排除结论。否则返回一份紧凑的报告。内容包含优先级、触发条件、影响、当前归属、验收接缝和证据。
6. **按下述优先级策略排序。** 若获准实施，调用项目的测试编写工作流，在最外层的实用接缝处证明旧行为变红。修复、评审，并附验证证据更新台账或报告。

## 优先级策略

当问题可能导致用户可见的卡死或报错、内存/磁盘增长、请求处理被阻塞、数据丢失、全网规模的放大，或阻塞后续工作的毒丸数据时，排最高优先级。

优先选择能给既有工作加上边界的低风险修复：按页流式处理、尊重背压、合并调度、把毒丸行挪到一边、跳过已证实的无操作，或让一次穷举搜索以终态结论收尾。安全上限是病态防护，不是常规产品限额：把它设在合法的大规模负载之上，达到时发出可操作的遥测，并定义接下来会发生什么。

不要仅凭吓人的数字排优先级：

- 当被轮询的状态有真实的恢复归属方、且最终能够改变时，轮询可以永远继续。要修复的是永远无法自愈的状态，而不是仅仅活得久的定时器。
- 廉价且有界的数据库工作即使没有生产证据也可接受。不要只为减少一个不大的固定查询次数，就去构建投影、缓存、游标状态机或另一套读模型。
- 当信息可能很快支撑产品 UI 或行为时，不要把它优化掉。

## 护栏

- 保全自愈能力。缓存或无操作捷径必须保留廉价的恢复信号，并在漂移、不确定、重启或先前失败时回退到普通的对账流程。
- 恢复式扫描必须要么跑完，要么把前进进度持久化。对于本地可修剪的命名空间，优先一次完整扫描、把上限设得足够高以能指示病态，而不是一个寻常的大项目。对于确实巨大的命名空间，持久化一个游标并从其后恢复。找到目标会更新身份标识；穷举未命中或异常触顶则产生该领域的终态结论。绝不让同一个部分前缀永远重启。
- 把可重试失败与终态失败分开。永久性拒绝不能永远占据队首或固定前缀。
- 为传输的两端和每个持久化/内存队列设定边界。写明溢出行为；绝不静默丢弃已接收的持久化数据。
- 按最坏的编辑操作评判缓存、索引或增量协议，而不是按安静时的平均值：向长期保留的集合插入、远离活跃视图的变更、移动、删除。在断言精确结果的同时断言工作量有界。
- 在信任一个压测工作负载的数字之前，先确认它做了它声称做的事：施加的力确实相交、路线确实被走完、失败分支确实运行。失败分支也要测量。
- 把成本测量与进程中其他一切运行的东西隔离开。
- 让兼容性工作匹配产品生命周期。在上线前的代码里，优先直接修改；除非真实的持久化数据有要求，不加遗留分支或迁移。
- 每个引入或修改的限制都必须有可观测的日志或指标，包含限制类型、配置的边界、受影响的归属方和过载后果。

## 完成标准

只有当每一条发现都有生产触发条件、量化的放大倍数、优先级依据、验收接缝和记录在案的处置，且每一条被排除的候选都说明了是哪个边界或自愈机制使其可接受时，审计才算完成。只有当红/绿证明同时展示了工作量有界**和**恢复能力持续时，实现才算完成。
