# 编写测试

好的测试**只**在真实行为被破坏时失败，并在每一次保持行为的重构或配置变更中保持通过。大多数坏测试以相反的方式失败：无害变更时变红，真实路径坏掉时反而变绿。下面的每条规则都服务于这一个目标。

要判断某处覆盖是否增添独立证明、应放在哪里，或哪些既有测试可以删掉，使用 [audit-tests](../audit-tests/SKILL.md)。

## 工作流：曳光弹，不是批量

1. **一次只写一个测试。**先写断言，看它在未修复的代码上变红，让代码挣得绿色，学到东西，再写下一个。绝不要预先批量写：针对*想象中*的行为批量写出的测试，钉住的是你的猜测——机制坏掉时它们照样通过，一切正常时它们反而失败。每个绿色循环都会告诉你下一个测试真正该断言什么。
2. **在最快的聚焦运行器上迭代**（一个文件、一个测试名），完整套件只在交付前的最后一道门禁运行。检查退出码，而不只是输出——什么都不打印的运行器和绿色运行看起来一样。遇到失败时，修复任何一个之前先读完每一条红色测试；它们往往共享同一个根因。
3. **在宣布完成之前**，证明测试会失败（见下文），并走一遍评审清单。

## 断言什么

- **通过最外层实际入口观察到的行为**——返回值、退出码、持久化的行、HTTP 响应、渲染输出——绝不是哪些内部函数运行了、值是怎么算出来的。针对公共表面的测试能挺过底下一切的重写；伸进内部的测试在每次重构中都会坏掉，钉住的是实现，不是行为。孤立的单元测试只留给真正棘手的纯逻辑（解析器、调度器、状态机）。
- **编译器已保证的东西一概不断言。**重新断言类型签名的测试——字段形状、被拒绝的参数类型——只有编译器先失败才可能失败。把预算花在业务规则、算术、分支、顺序、边界情况、副作用上。
- **断言实际值，而不是集合大小。**对去重/归一化/幂等路径，`length == 1` 在归一化坏掉时照样通过；还要断言存储值等于预期的规范形式。
- **能展示行为的最小规模。**两个实体加一个机制，先于人群和集成；小测试失败得快、状态可读，也不会在一条断言里缠上五种行为。
- **设计契约，而不是当前行为。**测试变红时，本能反应是重新测量并钉住新数字——要抵制它：按代码当前所作所为准绳校准的标尺，会把缺陷悄悄编码成基线。按声明的契约写断言，让代码去挣得它；如果没有契约存在，那是该问属主的问题，不是拿来测量后钉死的数字。只有契约本身变了，重新校准才正当。
- **确定性论断收紧，随机论断按分布断言。**每次运行都成立的不变量给精确阈值。任何有噪声或依赖调参的论断（"A 通常胜过 B"、"负载均衡分布"）必须在一组运行/种子上按区间断言——对随机结果做单样本钉死，不是弱测试，而是**盲**测试：它认证的只是那个侥幸样本的行为，并可能把系统性偏差掩盖数月。如果必须断言一个有噪声的差值，放宽边界并在注释中注明它是混沌边界（chaos-marginal）。

## 接缝与打桩

- **不要把测试耦合到配置——在接缝处打桩。**以某个真实配置值为键的测试（哪个开关开着、哪个套餐是默认），在有人正当编辑配置时就会坏。修复方法绝不是 `skipIf`/条件判断——被跳过的断言会藏起耦合并停止覆盖该路径。给函数喂固定输入，或把查找打桩，让夹具 id 解析到固定值。试金石："如果某个配置值变了而逻辑没变，这个测试会坏吗？"
- **不要过度打桩——每个桩都是一个被冻结的假设。**在系统边缘打桩（网络、时钟、文件系统、第三方 SDK、配置查找），绝不桩内部协作对象。给内部对象打桩等于把它的当前契约硬编码；一重构，测试就撒谎。当存在可观察结果时，绝不让"是否以某参数被调用"充当主断言。为了测一个函数而桩掉三个内部模块，意味着：往上一层去测，在那里它们是真的。
- **宿主环境必须按生产方式接线系统。**如果一个缺陷只在真实环境里出现，说明宿主环境漏掉了生产总会设置的一项输入——修宿主环境，而不只是修缺陷。

## 控制变量与探针

- **每次比较只动一个变量。**把其他一切钉死——两组用同一种子、同样数量、同样配置；禁用不属于主体的机制。当比较测试失败时，先问是否有一个无关机制漏进了实验，然后再动被测代码。
- **验证，不要臆断。**绝不靠推理得出关于*原因*的结论——哪条路径触发了、失败从哪来——然后照此行动。写一个读公共状态并打印的一次性探针；似是而非的故事错得足够频繁，足以烧掉一整个会话，而一个探针就能让整个努力转向。探针是草稿：放在不可能被提交的地方，问题一有答案就删掉；如果该行为值得一个永久守卫，就把它升格为真正的测试。

## 测试跑在别人的在用机器上

一个抢占桌面的测试套件，是一个人们不再运行的套件。无论测试需要什么，它都取最低侵入性的形式：

- **绝不抢焦点。**不激活应用、不用 `makeKeyAndOrderFront`、不提升窗口、不移动指针、不向会话发送模拟点击、不播放音频。一个不得打断人的 UI 依然可以完整测试：构建窗口、驱动它的模型、在渲染出的视图上断言。当截图是证据时，在屏外捕获窗口自身的图像，而不是拍屏幕。把激活留在人触发的代码路径上，并通过调用处理函数来演练它，而不是反复启动应用。
- **绝不写入用户存放自身状态的地方。**让每个测试指向临时主目录、临时偏好域或偏好套件，以及临时安装位置。测试绝不能修改真实配置、资料库、登录项或已安装应用。生产代码可以读测试设置的覆盖项；当覆盖项不存在时必须表现正常。
- **不可避免可见的操作要成批执行。**如果某项检查确实需要真实启动，就在一次运行中完成它的全部观察，而不是每条断言重启一次，并在证据中注明它是可见的。
- **不留任何东西在运行。**测试启动的每个进程、窗口、服务器和临时文件都要停止并移除，失败时也不例外。

## 证明测试会失败

你从未见过失败的测试只是装饰。对任何回归测试——尤其是*在修复之后*写的——做一次证伪：按缺陷本会采取的方式回退或破坏生产代码，确认它因*预期的原因*变红，恢复，确认变绿。要核实回退确实生效：带错误 pathspec 的 stash 或 checkout 会无声地什么都没回退，"红色"运行悄悄测的是已修复的代码。迹象："红色"的数字与绿色数字相同。

## 变更之后测试变红时

在动手改任何东西之前，按可能性顺序分诊：

1. 测试编码的是**已被删除的语义**——它钉住的是旧实现的偶然行为。按契约的真实主张重新规格化它。
2. 实验**失控了一个变量**——一个新机制泄漏进来。把变量钉住。
3. **边界是混沌级地紧**。放宽它，并加注释说明。
4. 代码**确实错了**。探测状态，找出机制。

绝不为了一个测试通过而调常数却不重跑邻近测试：耦合的系统会重新洗牌。如果连续两次微调各自弄坏了不同的测试，停止戳弄——控制面错了；去找机制。

## 评审清单

对任何测试 diff 过一遍此清单，在同一遍次中落实修复，重跑套件：

1. 某条断言在复述类型保证？→ 删掉它。
2. 逻辑没变、只改配置它就会坏？或它以 `skipIf` 依赖配置？→ 在接缝处打桩。
3. 断言大多是针对桩掉内部对象的"以某参数被调用"？→ 往上一层、对着可观察输出去测。
4. 它钉住随机结果的单个样本？→ 按分布断言。
5. 在去重/归一化路径上只断言数量而不断言值？→ 补上值断言。
6. 被测函数在生产中还有调用吗？→ 如果唯一调用者是测试，把函数和测试一起删掉。
7. 它能因正确的原因失败吗？→ 证伪一次以确认。
8. 它抢焦点、移动指针、播放声音，或写入用户的真实配置、资料库或应用？→ 改为驱动模型和临时位置，并在屏外捕获窗口。
