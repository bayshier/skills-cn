# 评审

一个完成的变更只有通过三个视角的检验才配得上"完成"：它的**形状**、它的 **diff** 和它的**文档**。每个视角都有专门的技能。本技能只管它们管不了的——运行顺序、彼此之间的循环，以及一个总判定。

## 工作流

1. **定范围。**确定受评审的 diff，确认它有实质内容；琐碎编辑跳过整个流程。
2. **形状——[refactor-clean](../refactor-clean/SKILL.md)。**先运行它，趁重构还便宜，也赶在审计一个即将变动的 diff 之前。
3. **diff——[code-review](../code-review/SKILL.md)。**审计已定形的形状。一个迫使结构性改动的发现会把你送回第 2 步，而不是继续向前。
4. **文档——[write-docs](../write-docs/SKILL.md)。**更新本次变更触及的文档。然后从根 README 逐级追踪链接链直到每份文档：路径上的每个链接仍然可解析，且从中心到叶子的阅读流依然通顺有序。
5. **报告。**三个遍次合并成一个总判定——各自发现了什么、你改了什么、留下了什么以及为什么。只有当每个遍次都干净或已解决才算完成。

## 规则

- 进入一个遍次时，读它的技能——规则在那里，不在这里。
- 顺序约束的是呈现次序，不是披露时机：一有发现立即呈现，哪怕它属于后面的遍次。
- 循环，而不是级联：后面的修复若重开了前面的遍次，就回到那里。当完整走一遍不再带来任何东西时停止。
