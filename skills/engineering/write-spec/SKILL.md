# 撰写规格说明

把大型功能变成一梯子的小契约。每一级都应让人看得懂、让智能体可测试，并在整个功能完成之前就有用。

## 首要原则

1. **规划之前先盘问。**一次问一个问题，直到弄清期望结果、非目标、评审面、神圣契约、缺失资产，以及第一个有用的可游玩检查点。每个问题都附上你的推荐答案，让用户可以接受、拒绝或修改。代码能回答的问题就去检查仓库，不要开口问。访谈收尾时要问：计划是否必须携带向后兼容或数据迁移——默认是**都不要**：硬切换、不留兼容 shim、不留迁移脚手架、不搞部署顺序舞步。只有用户主动选择，才把它们放进计划。

2. **在 API 接缝处切片。**每个切片应尽可能表现得像一个小型库：命名的模块边界、带类型的输入/输出、确定的夹具，以及接缝处的测试。如果一个切片需要先启动三个不相干的系统才能检查，就把接缝磨得更利。

3. **调研迷雾。**当功能依赖不熟悉的领域、高保真视觉目标、具名参考物、基准、外部仓库、库，或"人们通常怎么做？"这类问题时，在敲定切片之前做有针对性的在线调研。优先一手来源：官方文档、源码仓库、论文、案例研究、演讲和已上线的示例。如果存在参考实现，在移植或近似之前先加一个复现 spike。

4. **让进度可见。**对视觉或交互工作，每个切片都应产出可游玩的东西：一条路由、一个夹具页面、一个宿主环境、一个 CLI 探针，或一个 HTML 可视化，供人运行、查看、截图和点评。测试证明契约；演示暴露品味与意图。

5. **优化反馈回路。**切片方式要让下一个有用的问题能被快速回答。优先选择微小的可运行表面、可热重载的宿主环境、样例夹具和自足的工作台，而不是那种要等整个功能存在后任何人才学得到东西的计划。对资产密集型工作，规划一个资产应用/工作台，让人和美术可以添加样本、上传替换物、实时预览，并快速看到校验失败。

6. **顺着仓库的天然形状。**如果仓库是 monorepo，就规划应用和包，而不是把一切都塞进当前应用。给每个可测试表面一个一等公民的路由或命令；当一个小型专属应用更清晰时，不要把新行为堆在不透明的查询开关后面。

7. **不因缺失输入而阻塞。**如果美术、数据、凭据或外部资产缺失，就规划生成式占位物加上一份替换契约。功能应带着占位物推进，同时由一条单独的交接路径确切说明人或外部合作伙伴后续必须提供什么。

8. **并行起草，然后综合。**对任何多切片功能，不要指望一个遍次找到正确的切法。扇出若干独立草稿，把最好的部分合并成一个计划（见工作流）。分歧正是要点——所以要在两个轴上工程化它：给每份草稿一个不同的*偏置*（它所优化的透镜），并且当有多个模型家族可用时，混用不同的*模型*。盲目的、偏置各异的草稿能浮现单个计划看不到的切片、接缝和风险——而在它们独立达成一致之处，你知道这个切法是扎实的。

9. **递归揭开战争迷雾。**第一版切片图是一次侦察遍次，不是战场已明的证明。起草之后，把每个高风险切片当作独立功能来审视。如果它藏着多个变量、未知的外部实践、未经验证的架构，或"实现时再说"，就把这个子集重切片并重复，直到每个下一层切片都只有一个问题、一个接缝、一个评审面和一个判定。

10. **每个切片只动一个视觉变量。**当一个切片要求一个遍次匹配最终主视觉图时，视觉切片就失败了。按被评判之物拆分：密度、轮廓、颜色、纹理、光照、雾、水体位置、水体材质、标签可读性、动画节奏。每个切片获得一个裁剪/遮罩，以及只针对该变量的判定。整幅对比属于合成/集成阶段，在各变量拥有自己的证据之后。

## 工作流

1. **访谈：**持续提问，直到你能不含糊地叫出每个切片的名字。当剩余未知可以安全地交给第一个切片去发现时停止。
2. **调研：**当功能点名了参考物、库、技术、标准、视觉目标或性能模式时，起草之前先检查仓库并调研不熟悉的外部实践。把发现的源码/仓库/文章/论文链接记录进规格说明，并在移植切片之前把任何范本变成复现 spike。如果既有实验已经确立了公认做法，在起草替代方案之前先应用下文的**从调研到实现**。
3. **并行起草：**对多切片功能，生成**至少三个独立子智能体**起草整个计划——各自全新上下文，如需运行或构建来验证则各给一个 git worktree，否则让它们内联返回计划。三是下限，不是定数：随功能复杂度扩容草稿池，问题支持的每一种真正不同的方法或透镜都加一个起草者。给每个起草者访谈得出的*同一份*任务书，此外别无他物（绝不给其他草稿）——但给每个指派一个**不同的偏置**，让它们的分歧是结构化的，而不是偶然的。基准三件套：
   - **A——最少切片偏置：**仍能交付的最小梯子；激进合并切片，质疑每一级。
   - **B——风险优先偏置：**把最吓人的未知放在最前；排列切片顺序，让假设一错计划就快速死掉。
   - **C——接缝质量偏置：**优化每个接缝处的 API 边界、所有权与可测试性，哪怕代价是更多切片。

   当功能需要时换入或增加透镜（如资产管线偏置、性能偏置、迁移安全偏置），但保持偏置正交——靠增加新透镜扩容草稿池，绝不重复运行同一个透镜。同时**混用模型家族**：如果你当前被指示用 codex 起草，就至少有一份草稿用 claude——反之亦然——让草稿池平衡不同模型的盲区，而不只是不同的提示词。家族指厂商（claude vs codex），不是档位：每份草稿都用最先进的模型；绝不靠降到同家族更弱的档位来做多样化。每个起草者：侦察真实代码与测试（实测事实、失败过的做法、范围防火墙、可 grep 的文件/测试名），然后提出切片图、包/应用边界、依赖关系、API 接缝、可游玩交付物、验证门禁和人工评审检查点。只有真正单切片的问题才跳过扇出。
4. **综合：**读每份草稿，亲自构建权威计划——不要加冕其中一份。取最强的切片法，并集各草稿独自发现的接缝、风险和防火墙；在草稿分歧之处选论证更充分的判断，并把真正存在的备选记录给人。草稿独立一致之处你有坚实的地面；草稿分裂之处才是最需要深思的地方。当功能有任何视觉表面时，把 [screenshot-critique](../../visual/screenshot-critique/SKILL.md) 设为 README 中的常设验证门禁，让每个视觉切片继承它：规格说明必须指示实现智能体在接受任何视觉画面之前，运行一次无偏的 screenshot-critique 作为最后一道检查。只要某个切片的画面有可对比的目标——它所改变的先前外观，或为该功能添加的参考/灵感图——规格说明还必须点名 [compare-screenshots](../../visual/compare-screenshots/SKILL.md) 作为判定候选对目标的门禁：这是 screenshot-critique 单画面之眼给不出的遥测数据和"更少错误"式判定。
5. **递归迷雾审计：**逐切片评审权威图。对任何藏有隐藏变量、宽泛动词（"做得真实一点"、"对齐参考"、"加上后端"）、缺失调研、或多于一个视觉变量/API 接缝的切片，把同样的切片逻辑当作子功能在该切片上运行。持续重复，直到下一个实现切片能被一个聚焦产物接受或拒绝。把延后的变量记录为后续切片，而不是当前切片里的散文。退出判据是**决策预算**：当实现智能体继承决策而不是现场做决策时，切片才算完整规格化——每一处留白的自由，要么在切片文件中写明是受委派的，要么该切片还需要再切一遍。
6. **物化：**当功能多于一个切片，或需要资产/可视化时，创建 `specs/<feature>/`。
7. **对计划做 refactor-clean：**对物化后的规格说明运行 [refactor-clean](../refactor-clean/SKILL.md)——计划也是架构，它必须描述代码库假如今天设计会想要的形状，而不是带着硬加功能的旧形状。点名每个应拥有单一属主的概念（投影、环境、数据契约、渲染器阶段、状态机、测试 oracle），并确认没有任何切片引入平行抽象、重复概念或必须由后续切片删除的兼容层。某切片确实需要的过渡性脚手架，必须命名为带显式移除条件和移除它的切片编号的短命接缝——消费者一迁移就收拢，绝不默认带到最后。把由此形成的单一属主不变量和终态（"读起来像今天设计的，而不是硬贴上去的"）编码进 README，让每个实现遍次继承它们。
8. **回溯审计：**对话会死，规格说明长存。在宣布计划完成之前，清查完整对话和每份更早的规划产物（地图、访谈笔记、草稿）中只存在于那里的内容——带理由的决策、带败因的落选备选、中途的范围变更、用户给出的约束，以及决定了某些事的随口之言。每一条要么落进它的属主规格说明文件，要么被有意舍弃；范围变更要传播到每处引用它的地方，而不只是它落地之处。然后重读每份被规格说明取代的、仍然存留的前规划产物（一份地图的启动提示词、开放问题清单或提议计划），给被取代的小节加上指向计划的标记——过时指令不得有能力把新智能体引错路。当每条对话中的决策都能在规格说明里找到，且没有任何存留产物与梯子矛盾时，审计完成。
9. **逐切片构建：**在依赖某个切片之前，让它留下可运行的产物和验证。保持每个产物足够小、可以快速迭代。保持 README 的"Next Agent Prompt"写成未来智能体应当阅读并遵循的交接文本。
10. **工作说了算时重切片：**如果实现遇到障碍、切片开始改变无关变量——或决策台账不断由同一个切片填充——停止扩张补丁。先更新规格说明：把切片拆成更小的契约、点名冻结的输入、把多余的视觉变量移到后续切片，并重写 Next Agent Prompt 使其从第一个新切片恢复。然后继续。重切片是进展，不是失败。

## 从调研到实现

按不可变身份冻结已采纳 spike 的可运行代码、依赖、配置、输入、提示词/技能和证据。检查它实际做什么；选项名和摘要不是行为的证明。

在规格说明中映射**已证明的行为 → 证据 → 属主切片 → 对等门禁**。给每个起草者这份契约以及调研结论的边界。把用户要求的差异与未经检验的提议分开；清理不得悄悄重新设计胜出方案。

规划一次早期的生产入口对比：对照冻结参照物，用匹配的输入和受控的响应。检查计算出的请求、决策和完整输出；点名被允许的差异。每一行保留项都需要一个属主和一项检查。在高成本确认之前先运行对等校验，并保留原有质量门禁。

## 计划目录

`specs/<feature>.md` 只用于小型的单切片问题。大型功能放在：

- `specs/<feature>/README.md`——目标、背景、切片图、评审地图、契约、防火墙、已知未知，以及一个"Next Agent Prompt"小节，含当前状态、下一个接续点、全局 TODO 清单和下一遍次的交接指令。
- `specs/<feature>/slices/<NN>-<name>.md`——每个文件一个可独立验证的切片。
- `specs/<feature>/visualizations/*.html`——路线图、原型、宿主环境模型、生成的报告、拼版样图（contact sheet），或其他可供人评审的产物。
- `specs/<feature>/assets/`——参考图、夹具、截取图像，以及评判工作所需的其他输入。

对视觉工作，把功能自有的视觉证据保存在规格说明目录里：灵感图、参考截图、归档基线、对比拼版样图、生成的候选拍摄图，以及点评产物。如果这些文件一开始在规格说明目录之外，当它们成为功能评审上下文的一部分时，把它们复制进规格说明目录。产品快照目录仍可持有其宿主环境所拥有的活跃回归基线，但不要把这些可变输出或外部路径当作功能曾被对照评判的唯一记录。

## 切片文件契约

每个切片文件回答：

- 它解锁什么契约？
- API 接缝是什么：模块、函数/类型、数据形状、所有权？
- 人能运行或看到什么？
- 哪些测试、场景、截图、探针或性能门禁验证它？
- 如果切片产出任何视觉画面（截图、GIF、拼版样图或屏上渲染），切片文件必须指示实现智能体在切片被接受之前，把 [screenshot-critique](../../visual/screenshot-critique/SKILL.md) 作为最后一道检查——这是回归门禁和实现者自己的检查都供不出的未受暗示的第二意见。把它写成切片里显式的验证步骤，而不是顺带一提。
- 如果切片的画面有可对比的目标——它所改变的先前外观，或为该功能添加的参考/灵感图——切片文件还必须指示智能体使用 [compare-screenshots](../../visual/compare-screenshots/SKILL.md) 来判定候选对目标：遥测数据加"更少错误"式判定，而不是检查画面是否与参考一致。也要写成显式步骤。
- 对带参考图的视觉切片，写明**切片变量**和用于评判它的**裁剪/遮罩**。同时列出明确不在范围内的可见错误。示例：草地密度切片只比较下三分之一覆盖率和衰减；悬崖形状、悬崖纹理、水、天空和雾是后续切片。悬崖轮廓切片只比较山脊线和纵深排；岩石纹理和霾是后续切片。
- 哪些决策被委派给实现者？写明有意留白的自由（内部结构、命名、可逆的装饰性调用）。其余一切必须由切片解决：实现者不得不自行发明的未列明决策，是落入决策台账（[audit-choices](../audit-choices/SKILL.md)）的规格缺口，不是实现者的自由裁量。
- 什么必须保持绿色？
- 来自人的什么反馈会改变这个切片？
- 如果切片带人工评审检查点，切片文件必须把它框定为**非阻塞**：告诉实现智能体用 [preview-shots](../../visual/preview-shots/SKILL.md) 为用户打开画面，留出一个短暂窗口（约 5 分钟）等待回应，如果用户保持沉默——就基于证据决定，把决策和理由记录进规格说明，关闭已打开的画面（preview-shots 会清理 Preview，通宵运行因此绝不堆积窗口），然后继续。实现绝不为等待签核而停滞；检查点是纠正可逆判断的机会，不是阻塞构建的门禁。

## README 交接提示词

每个多切片规格说明的 README 都要在靠前位置有一节"Next Agent Prompt"。用第二人称写，写成未来智能体恢复该功能时应读的提示词。README 不应只声称自己是活跃交接状态；这一节本身必须直接告诉下一个智能体接下来做什么。它应包含：

- 当前状态和最后更新日期。
- 确切的下一个接续点。
- 活跃的阻塞项或警告。
- 一份全局 TODO 清单，每项都指向拥有它的切片。
- 给下一个智能体的直接指令：结束其遍次之前更新本节。

关键在于：一个新智能体打开 README 就知道接下来做什么，无需读聊天记录。

## 完成

当一个新智能体无需对话就能从切片 1 开始、且人无需逆向工程一堵文字墙就能评审路线图时，功能计划就完成了。

当所有切片都交付后，[close-spec](../close-spec/SKILL.md) 把计划归档到 `specs/done/`，并把它从构建梯子改写为持久的理由记录。
